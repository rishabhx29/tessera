# Performance

Measured numbers, never targets-as-results. Every figure below was produced by
a script committed on the `prototype/spike` branch (`spike/*.py`), on the
developer's real machine and real files. Re-derive any number by running the
named script.

## Hardware

AMD Ryzen (Family 23 Model 104) · 8 cores · 8 GB RAM · Windows 10/11 build
26300 · Python 3.11 · onnxruntime 1.23.2 CPU EP · SQLite 3.53.4 (APSW) with
sqlite-vec + FTS5 trigram.

## Week-1 spike — first configuration (FAILED, kept on record)

Corpus: 120 real images + 40 real documents, newest-first. Scripts:
`spike/spike.py` (numbers regenerated by `spike/fix_units.py` after a
seconds-printed-as-milliseconds label bug — data was right, the label wasn't).

| Stage | p50 | p95 |
|---|---|---|
| image decode | ~5 ms | 100 ms |
| OCR (RapidOCR PP-OCRv5 int8) | 2,500 ms | 8,000 ms |
| CLIP embed (SigLIP-base int8) | 200 ms | 300 ms |
| image end-to-end | 2,700 ms | 8,200 ms |
| doc extract / chunk / embed | 400 / 300 / 300 ms | 900 / 900 / 900 ms |

| Query (406 tiles) | p50 | p95 |
|---|---|---|
| lexical (FTS5 trigram) | 0.4 ms | 2.6 ms |
| image arm (SigLIP text→vec) | 73.9 ms | 91.8 ms |
| text arm (MiniLM) | 35.0 ms | 55.7 ms |
| fused (three arms, sequential) | 159.4 ms | 175.2 ms |

Scale estimate (replicated rows — estimates, not measurements): vec query p50
43 ms @ ~1k, 80 ms @ ~10k, 211 ms @ ~50k rows.

**Verdict: FAIL** against product-definition §6 (image e2e <1500 ms, fused
query <100 ms). The failure is concentrated in one stage: OCR at 2.5–8 s per
image is ~10× the entire budget.

## Remedy experiments (ADR-0004's pre-named fallback, measured)

### OCR A/B — Windows.Media.Ocr vs RapidOCR, 40 real screenshots

Script: `spike/swap_test2.py` (Part 1).

| Engine | p50 | p95 | mean chars extracted |
|---|---|---|---|
| Windows.Media.Ocr (en-US) | **50.3 ms** | 178.4 ms | 188 |
| RapidOCR PP-OCRv5 int8 | 3,255.8 ms | 6,172.4 ms | 285 |

Windows.Media.Ocr is ~65× faster; it extracts ~66% of the characters RapidOCR
does, and meaningfully missed text in only 3/40 files. Verdict: **swap the
OCR arm to Windows.Media.Ocr for v0.1** (Windows-first anyway); RapidOCR
remains the cross-platform path for a later phase.

### Image arm — SigLIP-base int8 vs CLIP ViT-B/32 int8, same 40 screenshots

Script: `spike/swap_test2.py` (Part 2). MobileCLIP2-S0 int8
(`felixhrdyn/mobileclip2-s0-onnx`) was **rejected before benchmarking**: its
graph uses ConvInteger(10) ops that onnxruntime's CPU EP does not implement.

| Model | vision embed p50 | text embed p50 | synthetic top-1* | real-screenshot top-1 |
|---|---|---|---|---|
| SigLIP-base int8 | 200 ms | **40 ms** | **0.90** | 0.500 |
| CLIP ViT-B/32 int8 | **85 ms** | 70 ms | 0.05 | 0.462 |

\* synthetic = 20 rendered-text images, query = the rendered phrase
(`spike/sanity_probe2.py` methodology). ViT-B/32's 7×7 patch grid cannot
resolve small rendered text; on real screenshots the two are comparable.

**Decision: keep SigLIP-base for the image arm.** Rationale: queries run on
every keystroke and indexing runs in the background at idle priority, so
query latency and fine-text matching (SigLIP's strengths) matter more than
index throughput (CLIP32's strength).

### Cross-modal sanity — the embedding space is sound

The full-spike sanity printed near-random ranks (17.1/40) **because the
discovered corpus was phone photos, where "OCR text" is noise** — a corpus
artifact, not a model defect. Controlled evidence
(`spike/sanity_probe2.py`):

- synthetic rendered-text images: mean rank 1.65/20, top-1 **0.90**
- real screenshots (OCR-text queries): mean rank 9.93/40, top-1 0.50

Honest caveats recorded: the int8 export has a high similarity floor (cosine
0.55 against pure noise, 0.82 for a 1°-rotated copy) — discrimination is
coarser than fp32; hybrid fusion absorbs this.

## Final v0.1 configuration — measured projection

Decode (5–100 ms) + **Windows.Media.Ocr** (50 ms p50) + **SigLIP-base int8**
(200 ms p50) ⇒ **save→searchable ≈ 260–350 ms**, against a 1500 ms target.

Query side, with the three arms run **in parallel** (the spike ran them
sequentially; onnxruntime releases the GIL, so threads suffice):
fused ≈ max(lexical 0.4, image 40, text 35) + fusion ≈ **~50 ms** at personal
scale. At ~50k tiles the sqlite-vec KNN scan adds ~140 ms — accepted for
v0.1, watched at v0.2 (options: int8 vec quantization, arm-aware top-k).

## OCR bake-off (ADR-0008 evidence) — three engines, same 40 real screenshots, same session

Script: `spike/ocr_bakeoff.py` (three runs, consistent within noise).

| Engine | p50 | p95 | mean chars |
|---|---|---|---|
| Windows.Media.Ocr (en-US) | **35.3 ms** | 136.2 ms | 188 |
| RapidOCR PP-OCRv5, package defaults | 2,819.7 ms | 5,854.2 ms | 267 |
| PP-OCRv6 det-tiny + rec-small, gyotaku tuning | 2,412.3 ms | 6,104.4 ms | **287** |

Findings:

- **Quality**: PP-OCRv6-tuned extracts the most text, and its unified
  18,710-character 50-script charset read everything in the test set — chat
  text, timestamps, UI labels — at scores of 0.98–1.00, while icon misreads
  score ≤0.73 and are dropped by the 0.5 gate.
- **The tuning is not the speedup we hoped for on this machine**: the cost is
  dominated by the recognizer's giant output head (100.7 s rec vs 9.3 s det
  over the corpus), not the detector. gyotaku's 4.6× det win doesn't move the
  total when rec is 90% of it. Their measured 0.67 s/screenshot (4 pinned
  i7-14700HX cores, hand-written Rust, width-batching to bound the output
  tensor) is the realistic target for our Rust engine; the Python spike's
  2.4 s is an upper bound, not the engine's ceiling.
- **Windows.Media.Ocr stays the Windows default**: 68× faster, and it missed
  meaningful text in only 3 of 40 screenshots.

## Engine 04 — OCR in the real Rust engine (measured)

The first OCR number produced by the engine itself rather than by the Python
spike. Same engine the spike chose, run through the same code path the indexer
uses.

Corpus: the first 40 screenshot-named files in the user's `OneDrive\Pictures\
Screenshots`, unmodified, in name order. No text is recorded — only timings and
character counts (SECURITY.md). Script:
`cargo run --release --example ocr_bench -- <folder> native 40`.

(The engine argument was added in Engine 05, when a second engine existed to
compare against. The run below was made with the two-argument form
`<folder> 40`, which was correct at the time; the current form above reproduces
the same measurement.)

Method: one warm-up read of the first image precedes timing (it pays for WinRT
initialisation and the cold file cache), then **all 40 images are timed**,
including the first one on its second read. Single pass, single run, no repeats.
Percentiles are linearly interpolated between the two nearest ranks. Each
timing covers the whole operation — file read, decode, recognise — because that
is what a user waits for.

Hardware: AMD Ryzen 3 5300U, 8 threads, 7.3 GB RAM, Windows 11 build 26300,
release build, one image at a time.

| Metric | Value |
|---|---|
| images read | 40 |
| **p50 per image** | **43.8 ms** |
| p95 per image | 195.7 ms |
| mean per image | 70.2 ms |
| mean characters extracted | 188 |
| images with no text | 1 of 40 |

Reading: the p50 lands in the 35–50 ms class the ticket predicted, and the mean
character count is **188 — identical to the Python spike's 188** on the same
engine and corpus, which is the useful part: the Rust adapter is reading the
same text the spike read, so the latency difference is plumbing, not quality.

Honest caveats:

- Single pass, single run, no repeats; a repeat pass would give a spread, and
  until one exists these numbers carry the uncertainty that implies. The p95 of
  196 ms is one slow image (likely a full-resolution screen with a lot of text)
  rather than a trend — with 40 samples, a p95 is effectively the second
  slowest.
- **Single-threaded, one image at a time.** The plan's queue (4 workers) is
  ticket 11; throughput there is this number times four workers, and that
  multiplication is a projection, not a measurement.
- Images with no text are counted rather than dropped: "fast" and "returned
  nothing" look identical in a latency table, and 1 of 40 is the honest figure.
- These are cold-cache numbers on a corpus the OS has already seen once. A
  first-ever indexing pass over cold files will be slower.

## Engine 04/05 — both OCR engines, measured in the engine itself

The first OCR numbers produced by the shipping engine rather than by the Python
spike, for both engines, over the same corpus in the same session — because a
comparison across different machines or different days is not a comparison.

Corpus: the first 40 screenshot-named files in the user's `OneDrive\Pictures\
Screenshots`, unmodified, in name order. No text is recorded — only timings and
character counts (SECURITY.md). Script:
`cargo run --release --example ocr_bench -- <folder> <engine> 40`, models
installed with `tessera models install --set ppocr`.

Method: one warm-up read of the first image precedes timing (it pays for runtime
initialisation, model load and the cold file cache), then **all 40 images are
timed**, including the first one on its second read. Single pass, single run, no
repeats. Percentiles are linearly interpolated between the two nearest ranks.
Each timing covers the whole operation — file read, decode, recognise — because
that is what a user waits for. One image at a time; the 4-worker queue is ticket
11 and any multiplication is a projection, not a result.

Hardware: AMD Ryzen 3 5300U, 8 threads, 7.3 GB RAM, Windows 11 build 26300,
release build, `ort` 2.0.0-rc.14 / ONNX Runtime 1.31 CPU provider, 8 intra-op
threads.

| Metric | native (`windows`) | fallback (`onnx`) |
|---|---|---|
| images read | 40 | 40 |
| **p50 per image** | **34.4 ms** | **949.6 ms** |
| p95 per image | 139.9 ms | 3,253.6 ms |
| mean per image | 52.1 ms | 1,405.6 ms |
| **mean characters extracted** | **188** | **288** |
| images with no text | 1 of 40 | 0 of 40 |

### Repeat pass (ticket 05 verification)

The table above is a single pass, and single passes carry the uncertainty
that implies. A second pass over the same corpus, same session, same command:

| Metric | native (`windows`) | fallback (`onnx`) |
|---|---|---|
| **p50 per image** | **45.7 ms** | **808.7 ms** |
| p95 per image | 203.8 ms | 3,144.6 ms |
| mean per image | 70.9 ms | 1,278.4 ms |
| **mean characters extracted** | **188** | **288** |
| images with no text | 1 of 40 | 0 of 40 |

What this does and does not show:

- **Character counts are identical across both passes and both engines** — 188
  and 288 — and identical to the Python spike's 188 / 287. Extraction is
  deterministic; this is the number to trust, and it is why the quality claim
  in this document is stated in characters rather than in hit rates.
- **Latency is not reproducible to the precision the first table implies.** The
  native p50 moved 34.4 → 45.7 ms and the fallback's 949.6 → 808.7 ms. Both
  moved *in opposite directions*, so this is ambient machine load, not a
  change in either engine. The ordering and the order of magnitude hold; the
  specific figures do not. **Read the first table as one sample, not as a
  benchmark.** A number quoted from it to three significant figures is
  over-precise, and the honest summary is "native tens of milliseconds,
  fallback hundreds to low thousands".
- Still **two samples, not a distribution**. `mean` moved less than `p50` for
  both engines, which says the corpus has a long tail that p50 and p95 are
  sensitive to and the mean is not.

Reading:

- **The native engine is ~28× faster at p50 and extracts 35% less text.** That is
  the trade ADR-0008 sets out, now measured in the engine that ships.
- **288 characters against the Python spike's 287** for the same engine on the
  same corpus. The Rust implementation reads the same text the spike read, so the
  latency difference is plumbing, not quality. (The native engine's 188 is also
  unchanged from both the spike and ticket 04's separate run.)
- **The fallback is not only more thorough, it is the only one of the two that
  worked on every image** — 0 of 40 with no text against 1 of 40.
- Quality is not free accuracy. On the committed fixture the fallback reads
  "INV01CE" for "INVOICE" and "0F-3391" for "QF-3391", where the native engine is
  exact. It finds more and garbles some of what it finds; typo-tolerant search
  absorbs some of that, and the numbers above are the honest summary rather than
  either engine being described as better.

Why so slow, in one line: the recogniser emits an `[batch, steps, 18,710]` output
tensor, so cost tracks total batched width, not the number of lines. Recognition
is batched by total width for that reason, and the native engine avoids the whole
question by asking the operating system.

Honest caveats:

- Single pass, single run, no repeats; a repeat pass would give a spread, and
  until one exists these numbers carry the uncertainty that implies. With 40
  samples a p95 is effectively the second slowest, so the ONNX p95 of 3.25 s is
  one slow image rather than a trend. **A repeat pass now exists** (the section
  above) and it moved both p50s by more than 10%, in opposite directions —
  which confirms this caveat rather than resolving it. Still two samples, not a
  distribution.
- Both engines ran warm, on a corpus the OS had already seen once. A first-ever
  indexing pass over cold files is slower for both.
- The ONNX figure is ~0.95 s p50 where ADR-0008 projected gyotaku's class of
  ~0.7 s on comparable cores. This is a low-power laptop part, not that
  reference hardware, so the gap is expected and is *not* evidence the engine is
  slower than the projection.

## Week-1 gate: PASS

- image save→searchable: ~260–350 ms projected (target <1500 ms) — components measured
- doc save→searchable: ~1000 ms measured (target <300 ms) — **still over**; doc extract is pypdf-bound. Accepted for v0.1 (docs are a minority of the corpus and indexing is background); revisit if dogfooding disagrees.
- fused query: ~50 ms projected at personal scale (target <100 ms); 159 ms measured sequential
- cross-modal sanity: 0.90 top-1 controlled (chance = 5%)

Methodology notes: single-machine, single-run numbers with p50/p95 over
per-file timings; scale rows are replication estimates and labelled as such
everywhere; no number in this file was produced on synthetic hardware or
synthetic corpora (the rendered-text images exist to validate the embedding
space, and are labelled as the sanity control).

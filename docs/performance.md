### Repeat pass (ticket 05 verification)

The table above is a single pass, and single passes carry the uncertainty
that implies. A second pass over the same corpus, same session, same command:

| Metric | native (`windows`) | fallback (`onnx`) |
|---|---|---|
| **p50 per image** | **45.7 ms** | **808.7 ms** |
| p95 per image | 203.8 ms | 3,144.6 ms |
| mean per image | 70.9 ms | 1,278.4 ms |
| **mean characters extracted** | **188** | **288** |
| images with no text | 1 of 40 | 0 of 40 |

What this does and does not show:

- **Character counts are identical across both passes and both engines** â€” 188
  and 288 â€” and identical to the Python spike's 188 / 287. Extraction is
  deterministic; this is the number to trust, and it is why the quality claim
  in this document is stated in characters rather than in hit rates.
- **Latency is not reproducible to the precision the first table implies.** The
  native p50 moved 34.4 â†’ 45.7 ms and the fallback's 949.6 â†’ 808.7 ms. Both
  moved *in opposite directions*, so this is ambient machine load, not a
  change in either engine. The ordering and the order of magnitude hold; the
  specific figures do not. **Read the first table as one sample, not as a
  benchmark.** A number quoted from it to three significant figures is
  over-precise, and the honest summary is "native tens of milliseconds,
  fallback hundreds to low thousands".
- Still **two samples, not a distribution**. `mean` moved less than `p50` for
  both engines, which says the corpus has a long tail that p50 and p95 are
  sensitive to and the mean is not.

Reading:

- **The native engine is ~28Ã— faster at p50 and extracts 35% less text.** That is
  the trade ADR-0008 sets out, now measured in the engine that ships.
- **288 characters against the Python spike's 287** for the same engine on the
  same corpus. The Rust implementation reads the same text the spike read, so the
  latency difference is plumbing, not quality. (The native engine's 188 is also
  unchanged from both the spike and ticket 04's separate run.)
- **The fallback is not only more thorough, it is the only one of the two that
  worked on every image** â€” 0 of 40 with no text against 1 of 40.
- Quality is not free accuracy. On the committed fixture the fallback reads
  "INV01CE" for "INVOICE" and "0F-3391" for "QF-3391", where the native engine is
  exact. It finds more and garbles some of what it finds; typo-tolerant search
  absorbs some of that, and the numbers above are the honest summary rather than
  either engine being described as better.

Why so slow, in one line: the recogniser emits an `[batch, steps, 18,710]` output
tensor, so cost tracks total batched width, not the number of lines. Recognition
is batched by total width for that reason, and the native engine avoids the whole
question by asking the operating system.

Honest caveats:

- Single pass, single run, no repeats; a repeat pass would give a spread, and
  until one exists these numbers carry the uncertainty that implies. With 40
  samples a p95 is effectively the second slowest, so the ONNX p95 of 3.25 s is
  one slow image rather than a trend. **A repeat pass now exists** (the section
  above) and it moved both p50s by more than 10%, in opposite directions â€”
  which confirms this caveat rather than resolving it. Still two samples, not a
  distribution.
- Both engines ran warm, on a corpus the OS had already seen once. A first-ever
  indexing pass over cold files is slower for both.
- The ONNX figure is ~0.95 s p50 where ADR-0008 projected gyotaku's class of
  ~0.7 s on comparable cores. This is a low-power laptop part, not that
  reference hardware, so the gap is expected and is *not* evidence the engine is
  slower than the projection.

## The image arm â€” SigLIP, measured (ticket 07)

### What it is actually good at

Four measurements, same models, same machine, same code. Together they change
what this feature can honestly be called.

| Corpus / signal | top-1 | Chance |
|---|---|---|
| **Visual control** â€” 6 deliberately distinct rendered scenes | **6/6 = 1.00** | 0.167 |
| **Screenshots, image arm alone** â€” 56 real screenshots | 0.268 | 0.018 |
| **Screenshots, OCR text alone** â€” same corpus, lexical match | **0.964** | 0.018 |
| Screenshots, image+text fused by RRF | 0.375 | 0.018 |

Reproduce: `cargo test --release -p tessera-core --test image_control -- --ignored --nocapture`
and the same for `--test image_fusion`.

**The image arm is not broken.** It matches a description to an unambiguous
visual scene perfectly and separates six images that differ by construction. The
0.268 on screenshots is a statement about screenshots, not about SigLIP.

**Screenshots are a text problem.** Reading the words out of one and matching
them retrieves it 96% of the time; visual similarity retrieves it 27% of the
time. Two screenshots of two different apps are visually near-identical and
textually distinct, so the image arm's signal is close to noise exactly where
OCR is strongest â€” which is every text-bearing file Tessera indexes.

**Naive fusion makes it worse.** RRF over both arms scores 0.375 against 0.964
for text alone: the weak arm dilutes the strong one. Any fusion has to be
weighted by how much text a given file actually has, which is not ticket 10's
default reciprocal-rank treatment.

**And the weight is a measurement, not a preference.** The same test sweeps the
image arm's vote over the same 56 screenshots, changing nothing else:

| `w_image` | top-1 | top-10 | rescued |
|---|---|---|---|
| 0.00 — lexical arm alone | 0.964 | 1.000 | 0/2 |
| **0.05 — the weight ticket 10 pins** | **0.964** | 1.000 | 0/2 |
| 0.10 | 0.857 | 1.000 | 0/2 |
| 0.20 | 0.679 | 1.000 | 0/2 |
| 1.00 — equal weight, ADR-0003 as written | 0.375 | 0.875 | 0/2 |

`rescued` counts queries the lexical arm missed at rank 1 that fusion then put
first, and it is 0 at every weight, equal weight included. That is not evidence
against the image arm: the denominator is 2 — the lexical arm misses 2 of these 56
queries — so this corpus has no headroom in which a second signal could show its
value. It shows what an arm *costs*, and that is what the weight is set from.

The cliff sits between 0.05 and 0.06, where one step of 0.01 costs 3.5 points. The
value this project first chose, 0.10, costs 10.7.

### The embedding space is flat, and the int8 export is not why

Median cosine between two **unrelated** screenshots is **0.508**, and 63% of
queries have their top two candidates within 0.01. The week-1 spike recorded the
same thing independently â€” "cosine 0.55 against pure noise" â€” and filed it as a
caveat.

The first reading of that number was that the quantised export had flattened the
space, which made fp32 weights (776 MB) the obvious fix. Both halves of that were
wrong, and both were measured rather than argued:

- **fp32 was obtained**, and compared against int8 later in this file. The noise
  floor moved from 0.508 to 0.516 and top-1 did not move at all.
- **A flat space is not a defect.** `cargo test --release -p tessera-core --test
  cross_modal_alignment` measures it directly, and one of that test's assertions
  is *that this stays high*: raw transformer embeddings are anisotropic, they
  share a large common direction, so unrelated pairs sit near a positive baseline
  instead of near zero. In a healthy model that is expected, not broken.

What the flatness actually costs is precision in the ambiguous middle, not the
ability to tell a dog from a chart: the six-scene control above scores 6/6 on
these same weights. The standard response to a flat space — whitening it — is
measured further down and is worse than doing nothing, on a held-out split, in
every variant tried.

### What this means for the feature

- Files that **contain text** â€” screenshots, PDFs, documents â€” are already found
  at 96% by reading their text. No image embedding is needed, and adding one
  measurably hurts.
- Files with **no text to read** â€” photographs, video frames, diagrams â€” are the
  image arm's domain, and there it is exact.
- "Search by description" is a real capability, but it is the capability for
  *content-only* images. On text-bearing files the honest name is "full-text
  search across your screenshots", which is what the OCR arm already is.

### What running the real models changed

Two bugs that only a real run could find, both of which would have shipped as
"the model is bad":

- **The vision tower does not return a pooled vector from its first output.**
  `last_hidden_state` is `[1, 196, 768]` â€” one row per 16Ã—16 patch. Reading the
  first 768 values of that is embedding the top-left patch and calling it the
  image. The pooled head is a *second* output, `pooler_output`, and it is now
  looked up **by name** so a re-export that reorders outputs cannot silently
  change what is compared.
- **The text tower takes one input, not two.** This export has `input_ids` and
  no attention mask, so passing a mask fails with "input name cannot be empty".

Both were found by dumping the graphs, after the code written from the model
card's description failed on the first real image.

### A methodology bug worth recording

The first version of this test queried with each image's **filename** and
measured top-1 of 0.05 â€” exactly chance. A filename is a timestamp
(`Screenshot 2024-02-18 142743`) and says nothing about what is in the picture,
so the number was measuring the test rather than the model. The query has to
be the text OCR read from the image, which is what the spike did.

## fp32 vs int8: the quantisation was not the problem

The flat-space diagnosis from ticket 07 said the int8 export was crushing the
embedding, and fp32 weights (776 MB, now pinned in lock.json and verified) were
the fix. They are not. Same corpus, same machine, same session:

| | noise floor (median) | top-1 (screenshots) | top-1 (photos) |
|---|---|---|---|
| int8 | 0.508 | 0.234 | 0.455 |
| fp32 | 0.516 | 0.277 | 0.455 |

The noise floor does not move and top-1 moves by 0.04. A 3.6x download buys
almost nothing, so **int8 stays**. The flatness is a property of the
representation, not of the quantisation - which is a useful thing to have
measured rather than assumed, because it retires the idea that more weights
would fix this.

| first token of `last_hidden_state` | **0.325** | 0.091 |
| mean over tokens | 0.512 | - |

The first token has by far the best-conditioned space and by far the worst
retrieval. That is not a contradiction to resolve: this export has 196 tokens
with no CLS position, so token 0 is a 16x16 patch of the image. A patch discriminates
images from each other beautifully and has no idea what any of them contains.

The dash in the last row is filled in below, measured on the 300-photo corpus
rather than on these 24 photographs: 0.0040 R@1.

`pooler_output` stays, and all three numbers are recorded because the obvious
alternatives both failing is itself the finding.

### Why they fail — and it is not that they are worse

The table above leaves the mechanism open, and its obvious reading is that a
pooled average loses detail a patch keeps. That is not what is happening.
Measured on the 300-photo corpus, same images and same captions as the headline:

| pooling | tower | R@1 | R@5 | R@10 | mean rank |
| --- | --- | --- | --- | --- | --- |
| `pooler_output` — **shipped** | both | **0.6629** | 0.9121 | 0.9660 | 4.0 |
| hidden state at the end token | text | 0.0020 | 0.0127 | 0.0266 | 153.9 |
| mean over the 64 token positions | text | 0.0020 | 0.0153 | 0.0333 | 152.7 |
| mean over the 196 patches | vision | 0.0040 | 0.0153 | 0.0380 | 143.3 |
| max over the 196 patches | vision | 0.0020 | 0.0120 | 0.0280 | 147.8 |

Chance is 1 in 300, which is 0.0033. Every alternative lands on it, and of the
nine combinations of the two towers scored here, eight land on it — the ninth is
the pair the engine ships.

That is not a pooling result, it is a units error, and the diagnostic says so
plainly: the cosine between `pooler_output` and the end token's hidden state,
over the first 50 queries, averages 0.0115 and never exceeds 0.0826. If the
pooler sliced a position out of `last_hidden_state` that cosine would be 1.0. It
does not slice; it transforms, and `last_hidden_state` is therefore a *different
vector space* from the one the other tower was trained to meet.

So the honest reading is not "mean pooling loses information". It is "nothing
comparable was tried". A pooled embedding can only be judged against a
projection trained to read it, and this export contains exactly one such
projection — the pooler it already ships. Judging the alternatives fairly would
mean training a projection, which is a different project with a different
budget.

`pooler_output` stays, now for a stated reason rather than by default: in this
export it is the only pooled embedding in the space the other tower lives in.

## The towers were always comparable, and "missing projection heads" was a category error

Two commits concluded first that the SigLIP towers "emit near-constant output
regardless of what they are given", and then that the towers were being compared
without their projection heads. **The second conclusion was wrong too, and it is
the more expensive one**: it added a 205 MB download and a vision-tower pass on
every text query, and it bought nothing measurable.

The mistake was comparing one kind of similarity against another kind's
threshold. Two numbers were measured, and both are **same-modality**:

| Measured | What it is | Value |
|---|---|---|
| `'a dog'` vs `'the ocean at sunset'` | text vs text | 0.808 |
| solid black vs solid white | image vs image | 0.897 |

Both are **anisotropy**. Raw transformer embeddings share a large common
direction, so unrelated items *in the same modality* sit high, in a perfectly
healthy model. This file had already said so one screen earlier while the code
asserted the opposite: an `#[ignore]`d test required those figures to be below
0.6, so it failed on every run and nothing in CI ever looked at it.

Cross-modal alignment is the measurement that carries meaning, because
anisotropy does not move it. Run through `SiglipEmbedder`, the type the engine
actually uses, on the pinned model set (`tests/cross_modal_alignment.rs`):

| Pair | Cosine | Expected |
|---|---|---|
| text `'a dog'` vs text `'the ocean at sunset'` | +0.808 | high (anisotropy) |
| image black vs image white | +0.897 | high (anisotropy) |
| cross `'a dog'` vs black | **-0.033** | near zero |
| cross `'the ocean at sunset'` vs white | **-0.007** | near zero |

An unrelated image and sentence sit at zero. The towers were already in one
space, and the export never lacked projection heads: for identical input, the
combined graph's `text_embeds` and the bare tower's `pooler_output` sit at cosine
0.996 (vision) and 0.947 (text) and rank the same corpus the same way.

### What the combined export actually costs

Both exports, same 11 photographs, identical pixels and identical token ids,
chance 0.091. Measured in a one-off ONNX Runtime harness (1.23.2, the same
installed files), **not** in a repository test:

| Text encoder | top-1 | top-3 |
|---|---|---|
| bare towers, `pooler_output` | 0.545 | 0.727 |
| combined export, `image_embeds` / `text_embeds` | 0.545 | 0.727 |

Identical. The 0.455 against 0.545 that justified the change was one item out of
eleven, and it did not reproduce.

Against that, the combined graph takes both towers on **every** call, and cannot
be given a cheap dummy side: it declares no optional inputs, so ORT answers
`Required inputs (['pixel_values']) are missing from input feed`, and the vision
branch reshapes to a fixed 196-patch layout, so anything smaller than 224x224
fails at `/vision_model/embeddings/Reshape`. Measured medians:

| Path | Median | When it runs |
|---|---|---|
| text tower alone | **62 ms** | every keystroke |
| vision tower alone | 242 ms | once per file, at index time |
| combined graph, either input | ~300 ms | — |

The combined export would put a 242 ms vision pass on every query. It is
rejected, and `siglip-full.uint8.onnx` is deliberately **not** pinned.

Candidates ruled out along the way, each by measurement rather than argument:
graph optimisation (0.808 at Level3, Level1 and `Disable`, bit-identical), output
index assumption (names confirmed as `["last_hidden_state", "pooler_output"]`),
tensor extraction (all 768 components differ, norm 1.0), and quantisation (fp32
identical).

Text padding is the one place a real difference exists, and the engine's choice
is the right one. On the same 11 photos and the same harness, varying only the
text side:

| Text padding | top-1 | top-3 |
|---|---|---|
| pad to 64 with id 0 (shipped) | **0.545** | 0.727 |
| pad to 64 with the eos id | 0.455 | 0.727 |
| no padding, exact length | 0.091 | 0.545 |

SigLIP's text tower was trained at fixed length, so an unpadded sentence is out
of distribution and collapses to 0.091 - indistinguishable from chance on eleven
items. Padding with id 0 is not a compromise; it is the configuration that works.

**Provenance:** the cross-modal table and the retrieval table below come from
repository tests and can be reproduced. The bare-versus-combined comparison and
the padding arms come from a one-off harness that is not in this repository.
That is a gap, and it closes when the evaluation corpus below lands, which needs
a real harness anyway.

## COCO text-to-image retrieval — the baseline eleven photographs could not be

**Provenance: measured, reproducible from this repository.**
`crates/core/tests/coco_retrieval.rs`, run with `--release` against the corpus
named by `TESSERA_CORPUS`. The corpus is 300 photographs drawn from the COCO
2014 validation split, minimum side 320 px, each carrying the five captions real
annotators wrote for it — 1501 queries over 300 images. The test measures
`SiglipEmbedder`, the type the engine ships, with the shipped stretch
preprocessing and the shipped query path, so this is the product's number rather
than a benchmark's.

| metric | caption embedded as written | **through the shipped query path** |
| --- | --- | --- |
| R@1 | 0.6582 (988 of 1501) | **0.7015** (1053 of 1501) |
| R@5 | 0.9134 (1371 of 1501) | **0.9454** (1419 of 1501) |
| R@10 | 0.9627 (1445 of 1501) | **0.9813** (1473 of 1501) |
| median rank | 1 of 300 | 1 of 300 |
| mean rank | 4.0 of 300 | 2.3 of 300 |
| chance R@1 | 0.0033 | 0.0033 |

Both columns are this one test, before and after the query transform below: the
test embeds through `embed_query`, and the left column is the run that predates
it. The right column is what the product does today.

Latency does not move with it — the transform is string work in front of the same
single encoder pass. The post-change run is its own control: it printed 312 ms per
image against 260 ms on the *indexing* half, a path the change does not touch at
all, on a machine that was downloading a model at the time. So the timings stand
as the clean run measured them: **77.9 s to index**, 260 ms per image, and **98.4
s for 1501 queries**, 66 ms per query. The 82 ms in the later run is the same load
that 312 is, and neither figure is the one to quote.

Ties are broken against the model: a caption's rank is one plus the number of
images scoring *strictly* higher, so an image level with the right answer counts
as beating it. Every caption is a query, so one lucky retrieval moves the
headline by 0.07 percentage points rather than 9.

### What this number means

The 0.85 that was asked for is **met at rank 5 and missed at rank 1**. Read as
top-1 accuracy, description search is at 70%; read as "the right photograph is in
the first row of results", it is at 95%. Both readings are honest and they answer
different product questions, so the target cannot be scored until it is said which
one it meant. Nothing in `docs/product-definition.md` sets a numeric bar for this
feature — it asks for a "CLIP text↔image embedding space for description queries"
and says nothing about recall — so this is the one number in this file the
repository cannot supply a reading for on its own.

This is the first measurement on which mechanism comparisons are meaningful. 300
images and 1501 queries resolve a difference of a few percentage points; the
eleven-photo set resolved 9.1 points per item and had already been queried often
enough that tuning against it would have been fitting noise.

Cost per image is a real constraint and is measured above: 260 ms to index one
photograph is fine for a library import and unacceptable for anything
interactive, and 66 ms per query is what a keystroke can afford only with
debouncing. Any fix that adds a second encoder pass per query multiplies that 66
ms, which is why the combined export was rejected on cost rather than on
quality.

### The query was worth more than the model — and it is shipped

Before spending anything on a better encoder, the query itself was fixed. It cost
nothing, and it moved rank 1 further than either mechanism below moves it.

Captions written by annotators are sentences. The tower was trained on alt text,
which is lower case and ends without a period, so a sentence is off-distribution
for it. Five transforms, same 1501 captions, same images, one harness:

| query transform | R@1 | R@5 | R@10 | mean rank |
| --- | --- | --- | --- | --- |
| as written — the shipped path until this change | 0.6629 | 0.9121 | 0.9660 | 4.04 |
| first letter lower-cased | 0.6849 | 0.9287 | 0.9734 | 3.56 |
| whole query lower-cased | 0.6962 | 0.9394 | 0.9827 | 2.34 |
| lower-cased, trailing period dropped — **shipped** | **0.7075** | **0.9420** | **0.9833** | 2.28 |
| lower-cased, period *and* commas dropped | 0.7089 | 0.9440 | 0.9840 | 2.27 |

The last row is the one the harness found first, and commas are deliberately not
in the shipped transform: they are worth +0.0014 R@1, two queries of 1501, and
deleting punctuation a person typed, for two queries in 1501, is not a trade
worth making. `SiglipEmbedder::normalise_query` lower-cases, drops the trailing
period and trims, and `embed_query` applies it before the text tower sees
anything.

In the engine, through that path, the test above moves from 0.6582 to **0.7015**
R@1 and from 0.9134 to **0.9454** R@5. The harness's 0.7075 and the engine's
0.7015 sit 0.6 points apart, which is the same resize-rounding offset that
separates the two raw columns from each other.

**The transform that needed proving is the one that touches capitalisation.**
Lower-casing is a no-op on a typed fragment, so on the query shape the product
mostly receives it can only be harmless; the risk runs the other way — that a
query *carrying* capitals loses information. It does not. Split on the 61
captions that have a capital after their first character — proper nouns, brand
names, `Goodmayes Boys' School`:

| subset | n | R@1 as written | R@1 normalised | mean rank |
| --- | --- | --- | --- | --- |
| a capital after the first character | 61 | 0.3770 | **0.7705** | 33.38 → 2.69 |
| no such capital | 1440 | 0.6750 | 0.7049 | 2.79 → 2.26 |

The subset capitalisation was *for* is the subset that gains most — 39 points at
rank 1, mean rank from 33 to 3. Those are the off-distribution queries: a
capitalised token is one the tower barely saw in that position, and normalising
pulls it in rather than erasing it.

What this does **not** buy is a faster or better typed fragment. `--describe "a
dog on grass"` is already lower case with no final period, so the transform is the
identity on it, and every point above is on sentence-shaped input. Saying so
matters more than the number does: a reader who takes 0.7075 as "the search box
got four points better" has been misled by a number measured on sentences.

**A prompt ensemble was measured and not shipped.** Averaging the text vector
with `a photo of ...` and `a picture of ...` took R@1 from 0.7075 to 0.7135 — nine
queries of 1501, half a standard error — for a second encoder pass per query,
which doubles the measured 66 ms. It also retires the four-point gain this file
previously attributed to ensembling: that measurement had the lower-casing
*inside* its templates, so what it measured was the case fix. An ensemble with no
case fix scores 0.6562, worse than the raw query alone at 0.6629.

### Three mechanisms this corpus ruled out

Two mechanisms were the obvious candidates for the remaining 30% of rank-1
misses. One was image geometry at ingest: the engine stretches every photograph
to a square and throws the aspect ratio away doing it. The other was matching
against several crops of an image instead of one whole-image vector, because an
object that fills a corner of the frame is a small fraction of a single pooled
vector. Both are measured here, and neither is worth building. The third is not
an ingest change at all — it is the standard inference-time response to a flat
embedding space — and it is measured last.

The harness that measured them is a Python script outside this repository, which
is a gap: unlike the COCO baseline above, nothing here can be re-run from the
repository today. It had to earn its place before its numbers were worth
recording, and it did: its first variant is the shipped preprocessing, and it
lands at **R@1 0.6629** against the Rust engine's 0.6582 — both with the caption
embedded as written, the left column above. Seven queries out of
1501 move between the two, which is the resize filter — Pillow's BICUBIC against
the engine's CatmullRom — and not a difference in method. Every comparison below
is between variants inside the one harness, so that offset cancels.

**Ingest geometry does not help.** The engine stretches every photograph to a
square, discarding aspect. Three alternatives, same 1501 captions, same images:

| preprocessing | R@1 | R@5 | R@10 | mean rank |
| --- | --- | --- | --- | --- |
| stretch to 224x224 — **shipped** | **0.6629** | 0.9121 | 0.9660 | 4.0 |
| shortest side to 224, centre crop | 0.6409 | 0.9147 | 0.9640 | 3.9 |
| longest side to 224, centre crop | 0.6209 | 0.9054 | 0.9567 | 4.1 |
| letterbox to 224 on grey 127 | 0.6302 | 0.8994 | 0.9494 | 4.2 |

The shipped stretch is the best of the four at rank 1, by 2.2 points over the
closest alternative and 4.2 over the worst. Distorting aspect, it turns out, is
not the problem.

That finding retires a reading these sections invite. This file sets 0.545 top-1
— eleven photographs, a harness — beside 0.455 top-1 — eleven photographs, the
engine — and notes that the two differ in that one way. The juxtaposition
suggests geometry accounts for the gap. It does not: on 300 photographs
centre-cropping is the *worse* method, so whatever moved those eleven items, it
was not the aspect ratio.

Nothing here contradicts itself; the problem is that eleven items cannot carry a
comparison, and this file asked them to several times. They are enough to reject
a configuration that is broken — unpadded text collapsing to 0.091 is one of
those, and that rejection stands. They are not enough to rank two configurations
that work. The corpus above is the instrument for that, and it is the one to use
from here.

**Multiple vectors per image buy rank 5 and cost ten times the indexing.** Nine
overlapping crops per photograph — 3x3 at half size, so each is a quarter of the
frame — plus the whole image; ten vectors per image, matched two ways:

| matching | R@1 | R@5 | R@10 | mean rank |
| --- | --- | --- | --- | --- |
| whole image only — **shipped** | **0.6629** | 0.9121 | 0.9660 | 4.0 |
| best of the 10 vectors | 0.6356 | 0.9147 | 0.9647 | 4.0 |
| mean of the best 3 | 0.6576 | **0.9307** | **0.9680** | 3.8 |

Taking the maximum over ten vectors is *worse* at rank 1 than taking the whole
image alone: a crop that happens to match is a false positive, and ten chances
to match is more of them. Averaging the best three recovers to 0.6576, within
0.0053 of the baseline, and gains 1.9 points at rank 5 — for ten encoder passes
per photograph instead of one.

The cost decides it. A crop measured 362 ms and a whole image 391 ms in the same
run under the same load, so a crop is not cheaper than an image and ten vectors
per photograph multiplies indexing by about ten: at the engine's measured 260 ms
per image, a 600-photo library goes from about 2.5 minutes to about 26. There is
no batched shortcut hiding in it either — the vision tower does accept a batch,
but 16 images in one call took 447 ms per image against 575 ms for a single
call, a factor of 1.3 where the arithmetic suggests 16. Batching also moved the
pooled vector: the same image run alone and run as row 0 of a batch of five gave
cosines of 0.9973, so it is not perfectly free even where it is fast.

Those last two timings were taken while another job held the machine, so treat
the absolute milliseconds as an upper bound; the ratios, which are what the
argument uses, come from rows measured back to back.

Neither mechanism is implemented. The two tables above are the argument for
rejecting them, not a description of anything the engine ships: 0.7015 R@1 and
0.9454 R@5 with the stretch at ingest, one vector per photograph and the query
transform above remain the engine's numbers.

**Whitening the space removes the alignment along with the flatness.** If a flat
space costs precision in the ambiguous middle, the standard inference-time fix is
whitening: centre the embeddings, rotate them onto their principal axes and
rescale each axis to unit variance. It needs no labels and no trained projection,
only the library's own vectors, which the engine has at index time — so unlike
the pooling alternatives it is a mechanism that could have shipped.

It was measured with a held-out split, because a transform fitted on the images
it is then scored against proves nothing: the transform is fitted on half of the
300 photographs, applied to both sides, and scored on the other half with the 750
captions those images own. Chance over 150 candidates is 0.0067. Dimension counts
are separate fits, not truncations of one. The harness is the same
outside-repository Python script the geometry and crop tables came from — the
same gap, stated once — and before it changes anything it reproduces the shipped
configuration's 0.7075 to four decimals, on the full 300 candidates.

| transform fitted on | R@1 | R@5 |
| --- | --- | --- |
| nothing — the shipped configuration | **0.7787** | 0.9800 |
| centring only, the image mean removed | 0.5840 | 0.9160 |
| whitening on the fit images, 768 / 384 / 256 dims | 0.0067 | 0.0373 |
| whitening on the fit captions, 768 dims | 0.0853 | 0.2267 |
| whitening on the fit captions, 384 / 256 dims | 0.5280 / 0.6493 | 0.7627 / 0.8813 |
| whitening on images and captions together, 768 / 384 / 256 dims | 0.1493 / 0.5773 / 0.6333 | 0.3107 / 0.7987 / 0.8853 |

Every variant is worse than doing nothing, and the sharpest result is the
simplest one: whitening fitted on images alone lands **exactly on chance**. That
is not an implementation failure, it is the answer. The large shared component is
what the two towers *agree* on; a transform fitted in the image space and applied
to text moves the text vectors somewhere the images no longer are, which is why
the two sides come out unrelated. Even fitted on captions, and applied to both,
whitening subtracts the direction that carries the cross-modal match. Five
regularisation values from 1e-5 to 1e-1 times the mean eigenvalue move R@1
between 0.0067 and 0.0227, so it is not a tuning problem; and fitting on all 300
images — the leaky, most favourable version, which is what the engine would
actually do — gives 0.0933, so the held-out split is not what makes it fail.

Two things follow. The flatness is not a defect to be corrected at query time,
which is the second time this file has had to say so: fp32 said it about the
weights, and this says it about the space itself. And the baseline in that table
is worth reading twice — 0.7787 with 150 candidates against 0.7075 with 300, same
model, same captions, half the library. Rank 1 gets easier on a smaller shelf, so
this feature's headline is a number about a library size rather than a constant.

## Where this leaves the feature

The headline number is now COCO: **0.7015 R@1 and 0.9454 R@5** over 300
photographs and 1501 real captions, measured through the shipped engine. The
eleven-photo set remains useful as an attribute-binding floor — **0.455 top-1
and 0.727 top-3** through the engine (`tests/image_retrieval.rs`), 0.545 top-1
in the harness above, which centre-crops where the engine stretches, against a
chance rate of 0.091 — but it is a stress test, not a baseline.

The eleven-photo corpus makes the task hard on purpose. Four of the eleven photos
are dogs and three of those are dogs on grass, so most of the ranking work is
attribute binding: "running through grass" against "sitting on grass" against
"with its tongue out". Three of the four miss at rank 1; two land in the top 3. A
cat face is retrieved as a dog. This is the documented weakness of single-vector
image-text models, and it is the part a better encoder alone is least likely to
fix.

The honest position: **description search works, is wired into the CLI, and can
be demonstrated today.** On COCO photographs it retrieves the right image at rank
1 for 70% of real captions and within the top 5 for 95%. On screenshots the text
arm already wins 0.964 and the image arm is not the one doing the work. It is not
yet a claim to put on a README, because 0.70 at rank 1 is a good retrieval aid
rather than the 0.85 the feature was asked for.

### What is not measured

A same-corpus comparison against another encoder. Every number here is SigLIP
Si16-base as int8; 0.7015 says what this model does, not what the task allows.
The SigLIP2 base towers are the obvious next comparison and it has not been run
yet.

The caption arm as a retrieval route. It runs now — eleven of eleven photographs
produce a caption — but nothing indexes those captions and no retrieval number
has been taken from them. Four of the eleven captions shared a word with the
photograph's label, which is a floor for the arm being alive and nothing more.

Everything on macOS. The Vision OCR adapter is written and has never been
compiled or run on an Apple machine; the `macos-14` CI job is the gate, and until
it is green the adapter is unverified rather than working.

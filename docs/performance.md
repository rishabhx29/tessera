### Repeat pass (ticket 05 verification)

The table above is a single pass, and single passes carry the uncertainty
that implies. A second pass over the same corpus, same session, same command:

| Metric | native (`windows`) | fallback (`onnx`) |
|---|---|---|
| **p50 per image** | **45.7 ms** | **808.7 ms** |
| p95 per image | 203.8 ms | 3,144.6 ms |
| mean per image | 70.9 ms | 1,278.4 ms |
| **mean characters extracted** | **188** | **288** |
| images with no text | 1 of 40 | 0 of 40 |

What this does and does not show:

- **Character counts are identical across both passes and both engines** â€” 188
  and 288 â€” and identical to the Python spike's 188 / 287. Extraction is
  deterministic; this is the number to trust, and it is why the quality claim
  in this document is stated in characters rather than in hit rates.
- **Latency is not reproducible to the precision the first table implies.** The
  native p50 moved 34.4 â†’ 45.7 ms and the fallback's 949.6 â†’ 808.7 ms. Both
  moved *in opposite directions*, so this is ambient machine load, not a
  change in either engine. The ordering and the order of magnitude hold; the
  specific figures do not. **Read the first table as one sample, not as a
  benchmark.** A number quoted from it to three significant figures is
  over-precise, and the honest summary is "native tens of milliseconds,
  fallback hundreds to low thousands".
- Still **two samples, not a distribution**. `mean` moved less than `p50` for
  both engines, which says the corpus has a long tail that p50 and p95 are
  sensitive to and the mean is not.

Reading:

- **The native engine is ~28Ã— faster at p50 and extracts 35% less text.** That is
  the trade ADR-0008 sets out, now measured in the engine that ships.
- **288 characters against the Python spike's 287** for the same engine on the
  same corpus. The Rust implementation reads the same text the spike read, so the
  latency difference is plumbing, not quality. (The native engine's 188 is also
  unchanged from both the spike and ticket 04's separate run.)
- **The fallback is not only more thorough, it is the only one of the two that
  worked on every image** â€” 0 of 40 with no text against 1 of 40.
- Quality is not free accuracy. On the committed fixture the fallback reads
  "INV01CE" for "INVOICE" and "0F-3391" for "QF-3391", where the native engine is
  exact. It finds more and garbles some of what it finds; typo-tolerant search
  absorbs some of that, and the numbers above are the honest summary rather than
  either engine being described as better.

Why so slow, in one line: the recogniser emits an `[batch, steps, 18,710]` output
tensor, so cost tracks total batched width, not the number of lines. Recognition
is batched by total width for that reason, and the native engine avoids the whole
question by asking the operating system.

Honest caveats:

- Single pass, single run, no repeats; a repeat pass would give a spread, and
  until one exists these numbers carry the uncertainty that implies. With 40
  samples a p95 is effectively the second slowest, so the ONNX p95 of 3.25 s is
  one slow image rather than a trend. **A repeat pass now exists** (the section
  above) and it moved both p50s by more than 10%, in opposite directions â€”
  which confirms this caveat rather than resolving it. Still two samples, not a
  distribution.
- Both engines ran warm, on a corpus the OS had already seen once. A first-ever
  indexing pass over cold files is slower for both.
- The ONNX figure is ~0.95 s p50 where ADR-0008 projected gyotaku's class of
  ~0.7 s on comparable cores. This is a low-power laptop part, not that
  reference hardware, so the gap is expected and is *not* evidence the engine is
  slower than the projection.

## OCR at corpus scale — 1,775 photographs whose printed text was transcribed

The bake-offs above rank engines on the format the OCR feature was designed
around: screenshots, where text is large, rendered and clean. They cannot answer
how often a word in a real *photograph* can be found, because 40 hand-picked
screenshots are a sample of one kind. This section measures that question on a
downloaded corpus: 1,775 real photographs whose signs, labels and graffiti
people transcribed (COCO-Text V2 over COCO images), queried through the shipping
engine and the shipping store.

**Provenance: measured, reproducible from this repository.**
`crates/core/tests/ocr_corpus.rs`, `--release`, against the corpus named by
`TESSERA_OCR_CORPUS`; the annotations zip is pinned by sha256 and the builder
script and images live beside the corpus, outside the repository (SECURITY.md),
like every other real-image corpus here. Both columns are the same 1,775
photographs, same machine, same day, one engine at a time. The corpus asks about
6,013 words over 1,686 photographs — every transcription that is legible,
English, at least four characters, and not a bare number (a number is a
substring of the image's own file name, and file names are indexed on purpose).

| metric | native (`windows`) | fallback (`onnx`) |
| --- | ---: | ---: |
| photographs yielding any text | 803 of 1,775 (45%) | 1,503 of 1,775 (85%) |
| characters per image, p50 | 0 | 17 |
| **transcribed words read** | **906 of 6,013 (15.1%)** | **2,622 of 6,013 (43.6%)** |
| **words findable end to end** | **913 (15.2%)** | **2,650 (44.1%)** |
| photographs answering every queried word | 74 of 1,686 | 287 of 1,686 |
| photographs answering none | 1,254 of 1,686 | 677 of 1,686 |
| p50 / mean per image | 25 / 27 ms | 148 / 216 ms |
| words OCR read that the store then lost | 0 | 0 |

The two metrics fail in different places. **Word read** means the engine's text
contains the transcription whole, case-folded, as a contiguous substring — a
word that OCR renders with a space counts as unread, which makes the figure a
floor. **Word findable** asks the real `search` for the word and expects the
right photograph back through the real SQLite trigram index. Neither engine lost
a word the store was given; in the other direction the store *gained* 7 words
(native) and 28 (fallback) that the strict read check called unread, because
`search` expands each term into lookalike variants (0/o, 1/l) and OCR misreads
characters into their lookalikes.

Reading:

- **On real photographs the native engine — the v0.1 default — finds 15% of the
  transcribed words; the fallback finds 44%.** The loss is upstream of the store
  and the query path: it is what the engine sees.
- **It sees nothing at all on 55% of these photographs** (972 of 1,775; the
  median photograph yields zero characters). This is a regime the OS engine was
  not built for: small frames (COCO caps the long side at 640 px) with small,
  stylised scene text — graffiti, distant shop signs — where on the screenshot
  corpus just above the same engine found text on 39 of 40 images.
- **The corpus's labels were spot-checked, not trusted**: the skate-park wall
  that transcribes as "DRUMER" and "SPOOBY" really carries that graffiti, so
  these low numbers are the engine's difficulty rather than annotation noise.
  Some labels are annotators' own hard reads; both engines pay the same labels,
  so the comparison between columns holds even where the absolute level is a
  floor on a hard corpus.
- **The fallback's price is a property of the library, not of the engine.** On
  screenshots it was ~28× slower at p50 (949.6 ms against 34.4); here it is ~6×
  (148 against 25), because the same width-driven cost that makes it slow on a
  2 MP screenshot is small on a 0.3 MP photograph.

Honest caveats:

- One pass each. A second fallback pass, run while other work was on the
  machine, gave p50 123 ms / mean 180 ms against 148 / 216 here, and the native
  engine moved 25–36 ms p50 across three passes — the same lesson as the
  screenshot bake-off's repeat pass: the ordering and the order of magnitude are
  the finding, and the specific figures are one sample.

### The per-file cascade, measured

The two columns put a product question on the table that neither answers on its
own: ask the fast engine first, and pay for the fallback only where the fast one
found nothing. The same harness measures it —
`a_native_then_onnx_cascade_reads_more_than_the_native_engine_alone`, Windows
only, because "the platform engine" in that sentence is `Windows.Media.Ocr`.

| metric | native | **native → fallback on an empty read** | fallback |
| --- | ---: | ---: | ---: |
| p50 per image | 25 ms | **73 ms** | 148 ms |
| mean per image | 27 ms | **85 ms** | 216 ms |
| photographs yielding any text | 803 (45%) | **1,529 (86%)** | 1,503 (85%) |
| **transcribed words read** | 906 (15.1%) | **1,644 (27.3%)** | 2,622 (43.6%) |
| **words findable end to end** | 913 (15.2%) | **1,658 (27.6%)** | 2,650 (44.1%) |
| photographs answering every queried word | 74 | **186** | 287 |
| photographs answering none | 1,254 | **861** | 677 |

Reading:

- **The cascade reads 81% more words than the native engine at about three
  times its mean cost, and about two-thirds of the fallback's words at 39% of
  the fallback's mean cost.** It is a real middle point, not a rounding error,
  and the store lost none of it either (14 words came back the other way,
  through lookalike expansion).
- **The bill is lower than the retry rate suggests.** The trigger fires on 972
  of 1,775 photographs (55%), and the whole run took 150 s against a projection
  of about 260 s — native's own pass plus the fallback at its average cost on
  those 55%: the photographs the native engine misses are the fallback's cheap
  ones, because the text-dense photographs that cost it the most are exactly the
  ones the native engine already read.
- **The union is bigger than either engine alone** — 1,529 photographs with any
  text, against the fallback's 1,503 and the native's 803 — because each engine
  is blind to a different handful.
- **The trigger is what holds the quality back, and it is deliberately the
  narrowest one.** An empty read fires only when native found *nothing*; on the
  803 photographs where it found anything — often a stray mark — the cascade
  keeps the native text and discards what the fallback would have read. A
  trigger that also fires on short or low-quality native reads would move the
  quality toward the fallback column and the price up with it; that version is
  not measured, and this table is what the cheapest form of the idea delivers.
- **On screenshots the same trigger would fire on 1 image in 40** (the one the
  bake-off above records as native's single empty read), so there the cascade
  is the native engine's speed with a fallback read once per forty images. That
  is arithmetic on measured numbers, not a run of the cascade over screenshots,
  which has not been made.
- **It is not shipped, and the default engine is unchanged.** Which engine
  ships is `preferred_engine`'s choice per platform (ADR-0008); this table is
  the evidence a change would need, and a decision to change it is not one this
  document makes.

## The image arm â€” SigLIP, measured (ticket 07)

### What it is actually good at

Four measurements, same models, same machine, same code. Together they change
what this feature can honestly be called.

| Corpus / signal | top-1 | Chance |
|---|---|---|
| **Visual control** â€” 6 deliberately distinct rendered scenes | **6/6 = 1.00** | 0.167 |
| **Screenshots, image arm alone** â€” 56 real screenshots | 0.268 | 0.018 |
| **Screenshots, OCR text alone** â€” same corpus, lexical match | **0.964** | 0.018 |
| Screenshots, image+text fused by RRF | 0.375 | 0.018 |

Reproduce: `cargo test --release -p tessera-core --test image_control -- --ignored --nocapture`
and the same for `--test image_fusion`.

**The image arm is not broken.** It matches a description to an unambiguous
visual scene perfectly and separates six images that differ by construction. The
0.268 on screenshots is a statement about screenshots, not about SigLIP.

**Screenshots are a text problem.** Reading the words out of one and matching
them retrieves it 96% of the time; visual similarity retrieves it 27% of the
time. Two screenshots of two different apps are visually near-identical and
textually distinct, so the image arm's signal is close to noise exactly where
OCR is strongest â€” which is every text-bearing file Tessera indexes.

**Naive fusion makes it worse.** RRF over both arms scores 0.375 against 0.964
for text alone: the weak arm dilutes the strong one. Any fusion has to be
weighted by how much text a given file actually has, which is not ticket 10's
default reciprocal-rank treatment.

**And the weight is a measurement, not a preference.** The same test sweeps the
image arm's vote over the same 56 screenshots, changing nothing else:

| `w_image` | top-1 | top-10 | rescued |
|---|---|---|---|
| 0.00 — lexical arm alone | 0.964 | 1.000 | 0/2 |
| **0.05 — the weight ticket 10 pins** | **0.964** | 1.000 | 0/2 |
| 0.10 | 0.857 | 1.000 | 0/2 |
| 0.20 | 0.679 | 1.000 | 0/2 |
| 1.00 — equal weight, ADR-0003 as written | 0.375 | 0.875 | 0/2 |

`rescued` counts queries the lexical arm missed at rank 1 that fusion then put
first, and it is 0 at every weight, equal weight included. That is not evidence
against the image arm: the denominator is 2 — the lexical arm misses 2 of these 56
queries — so this corpus has no headroom in which a second signal could show its
value. It shows what an arm *costs*, and that is what the weight is set from.

The cliff sits between 0.05 and 0.06, where one step of 0.01 costs 3.5 points. The
value this project first chose, 0.10, costs 10.7.

A second corpus agrees, from the other direction. `--test image_weighting` runs the
same design over **every** text-bearing image in the folder — 178 here, three times
the sweep's sample — and scores the lexical arm alone against both fusings:

| fusion, 178 screenshots | top-1 |
| --- | --- |
| lexical arm alone | 0.584 |
| weighted RRF, image arm at 0.05 | 0.579 |
| equal-weight RRF | 0.287 |

One query of 178 separates the lexical arm from the weighted fusion — 0.5 points
against a 3.7-point standard error — while equal weight costs 29.7. This corpus
has real headroom for a second arm (74 of its 178 queries are lexical misses) and
0.05 still does not take it, which is the answer the sweep gives as well: the
weight is set by what it costs, not by a benefit anyone has measured.

### The embedding space is flat, and the int8 export is not why

Median cosine between two **unrelated** screenshots is **0.508**, and 63% of
queries have their top two candidates within 0.01. The week-1 spike recorded the
same thing independently â€” "cosine 0.55 against pure noise" â€” and filed it as a
caveat.

The first reading of that number was that the quantised export had flattened the
space, which made fp32 weights (776 MB) the obvious fix. Both halves of that were
wrong, and both were measured rather than argued:

- **fp32 was obtained**, and compared against int8 later in this file. The noise
  floor moved from 0.508 to 0.516 and top-1 did not move at all.
- **A flat space is not a defect.** `cargo test --release -p tessera-core --test
  cross_modal_alignment` measures it directly, and one of that test's assertions
  is *that this stays high*: raw transformer embeddings are anisotropic, they
  share a large common direction, so unrelated pairs sit near a positive baseline
  instead of near zero. In a healthy model that is expected, not broken.

What the flatness actually costs is precision in the ambiguous middle, not the
ability to tell a dog from a chart: the six-scene control above scores 6/6 on
these same weights. The standard response to a flat space — whitening it — is
measured further down and is worse than doing nothing, on a held-out split, in
every variant tried.

### What this means for the feature

- Files that **contain text** â€” screenshots, PDFs, documents â€” are already found
  at 96% by reading their text. No image embedding is needed, and adding one
  measurably hurts.
- Files with **no text to read** â€” photographs, video frames, diagrams â€” are the
  image arm's domain, and there it is exact.
- "Search by description" is a real capability, but it is the capability for
  *content-only* images. On text-bearing files the honest name is "full-text

## fp32 vs int8: the quantisation was not the problem

The flat-space diagnosis from ticket 07 said the int8 export was crushing the
embedding, and fp32 weights (776 MB, now pinned in lock.json and verified) were
the fix. They are not. Same corpus, same machine, same session:

| | noise floor (median) | top-1 (screenshots) | top-1 (photos) |
|---|---|---|---|
| int8 | 0.508 | 0.234 | 0.455 |
| fp32 | 0.516 | 0.277 | 0.455 |

The noise floor does not move and top-1 moves by 0.04. A 3.6x download buys
almost nothing, so **int8 stays**. The flatness is a property of the
representation, not of the quantisation - which is a useful thing to have
measured rather than assumed, because it retires the idea that more weights
would fix this.

## The right tensor is still the wrong shape

Three candidate outputs were compared over the photographs in `TESSERA_PHOTOS`,
sampled to at most 24. The floors below reproduce to three decimals on the
eleven-photo set, which is where the top-1 column comes from — so they are a
property of the representation rather than of the folder:

| Output | noise floor | description search top-1 |
|---|---|---|
| `pooler_output` (shipped) | 0.591 | 0.455 |
| first token of `last_hidden_state` | **0.325** | 0.091 |
| mean over tokens | 0.512 | - |

The first token has by far the best-conditioned space and by far the worst
retrieval. That is not a contradiction to resolve: this export has 196 tokens
with no CLS position, so token 0 is a 16x16 patch of the image. A patch discriminates
images from each other beautifully and has no idea what any of them contains.

The dash in the last row is filled in below, measured on the 300-photo corpus
rather than on these 24 photographs: 0.0040 R@1.

`pooler_output` stays, and all three numbers are recorded because the obvious
alternatives both failing is itself the finding.

### Why they fail — and it is not that they are worse

The table above leaves the mechanism open, and its obvious reading is that a
pooled average loses detail a patch keeps. That is not what is happening.
Measured on the 300-photo corpus, same images and same captions as the headline:

| pooling | tower | R@1 | R@5 | R@10 | mean rank |
| --- | --- | --- | --- | --- | --- |
| `pooler_output` — **shipped** | both | **0.6629** | 0.9121 | 0.9660 | 4.0 |
| hidden state at the end token | text | 0.0020 | 0.0127 | 0.0266 | 153.9 |
| mean over the 64 token positions | text | 0.0020 | 0.0153 | 0.0333 | 152.7 |
| mean over the 196 patches | vision | 0.0040 | 0.0153 | 0.0380 | 143.3 |
| max over the 196 patches | vision | 0.0020 | 0.0120 | 0.0280 | 147.8 |

Chance is 1 in 300, which is 0.0033. Every alternative lands on it, and of the
nine combinations of the two towers scored here, eight land on it — the ninth is
the pair the engine ships.

That is not a pooling result, it is a units error, and the diagnostic says so
plainly: the cosine between `pooler_output` and the end token's hidden state,
over the first 50 queries, averages 0.0115 and never exceeds 0.0826. If the
pooler sliced a position out of `last_hidden_state` that cosine would be 1.0. It
does not slice; it transforms, and `last_hidden_state` is therefore a *different
vector space* from the one the other tower was trained to meet.

So the honest reading is not "mean pooling loses information". It is "nothing
comparable was tried". A pooled embedding can only be judged against a
projection trained to read it, and this export contains exactly one such
projection — the pooler it already ships. Judging the alternatives fairly would
mean training a projection, which is a different project with a different
budget.

`pooler_output` stays, now for a stated reason rather than by default: in this
export it is the only pooled embedding in the space the other tower lives in.

## The towers were always comparable, and "missing projection heads" was a category error

Two commits concluded first that the SigLIP towers "emit near-constant output
regardless of what they are given", and then that the towers were being compared
without their projection heads. **The second conclusion was wrong too, and it is
the more expensive one**: it added a 205 MB download and a vision-tower pass on
every text query, and it bought nothing measurable.

The mistake was comparing one kind of similarity against another kind's
threshold. Two numbers were measured, and both are **same-modality**:

| Measured | What it is | Value |
|---|---|---|
| `'a dog'` vs `'the ocean at sunset'` | text vs text | 0.808 |
| solid black vs solid white | image vs image | 0.897 |

Both are **anisotropy**. Raw transformer embeddings share a large common
direction, so unrelated items *in the same modality* sit high, in a perfectly
healthy model. This file had already said so one screen earlier while the code
asserted the opposite: an `#[ignore]`d test required those figures to be below
0.6, so it failed on every run and nothing in CI ever looked at it.

Cross-modal alignment is the measurement that carries meaning, because
anisotropy does not move it. Run through `SiglipEmbedder`, the type the engine
actually uses, on the pinned model set (`tests/cross_modal_alignment.rs`):

| Pair | Cosine | Expected |
|---|---|---|
| text `'a dog'` vs text `'the ocean at sunset'` | +0.808 | high (anisotropy) |
| image black vs image white | +0.897 | high (anisotropy) |
| cross `'a dog'` vs black | **-0.033** | near zero |
| cross `'the ocean at sunset'` vs white | **-0.007** | near zero |

An unrelated image and sentence sit at zero. The towers were already in one
space, and the export never lacked projection heads: for identical input, the
combined graph's `text_embeds` and the bare tower's `pooler_output` sit at cosine
0.996 (vision) and 0.947 (text) and rank the same corpus the same way.

### What the combined export actually costs

Both exports, same 11 photographs, identical pixels and identical token ids,
chance 0.091. Measured in a one-off ONNX Runtime harness (1.23.2, the same
installed files), **not** in a repository test:

| Text encoder | top-1 | top-3 |
|---|---|---|
| bare towers, `pooler_output` | 0.545 | 0.727 |
| combined export, `image_embeds` / `text_embeds` | 0.545 | 0.727 |

Identical. The 0.455 against 0.545 that justified the change was one item out of
eleven, and it did not reproduce.

Against that, the combined graph takes both towers on **every** call, and cannot
be given a cheap dummy side: it declares no optional inputs, so ORT answers
`Required inputs (['pixel_values']) are missing from input feed`, and the vision
branch reshapes to a fixed 196-patch layout, so anything smaller than 224x224
fails at `/vision_model/embeddings/Reshape`. Measured medians:

| Path | Median | When it runs |
|---|---|---|
| text tower alone | **62 ms** | every keystroke |
| vision tower alone | 242 ms | once per file, at index time |
| combined graph, either input | ~300 ms | — |

The combined export would put a 242 ms vision pass on every query. It is
rejected, and `siglip-full.uint8.onnx` is deliberately **not** pinned.

Candidates ruled out along the way, each by measurement rather than argument:
graph optimisation (0.808 at Level3, Level1 and `Disable`, bit-identical), output
index assumption (names confirmed as `["last_hidden_state", "pooler_output"]`),
tensor extraction (all 768 components differ, norm 1.0), and quantisation (fp32
identical).

Text padding is the one place a real difference exists, and the engine's choice
is the right one. On the same 11 photos and the same harness, varying only the
text side:

| Text padding | top-1 | top-3 |
|---|---|---|
| pad to 64 with id 0 (shipped) | **0.545** | 0.727 |
| pad to 64 with the eos id | 0.455 | 0.727 |
| no padding, exact length | 0.091 | 0.545 |

SigLIP's text tower was trained at fixed length, so an unpadded sentence is out
of distribution and collapses to 0.091 - indistinguishable from chance on eleven
items. Padding with id 0 is not a compromise; it is the configuration that works.

**Provenance:** the cross-modal table and the retrieval table below come from
repository tests and can be reproduced. The bare-versus-combined comparison and
the padding arms come from a one-off harness that is not in this repository.
That is a gap, and it closes when the evaluation corpus below lands, which needs
a real harness anyway.

## COCO text-to-image retrieval — the baseline eleven photographs could not be

**Provenance: measured, reproducible from this repository.**
`crates/core/tests/coco_retrieval.rs`, run with `--release` against the corpus
named by `TESSERA_CORPUS`. The corpus is 300 photographs drawn from the COCO
2014 validation split, short side never below 160 px, each carrying the five captions real
annotators wrote for it — 1501 queries over 300 images. The test measures
`SiglipEmbedder`, the type the engine ships, with the shipped stretch
preprocessing and the shipped query path, so this is the product's number rather
than a benchmark's.

| metric | caption embedded as written | **through the shipped query path** |
| --- | --- | --- |
| R@1 | 0.6582 (988 of 1501) | **0.7015** (1053 of 1501) |
| R@5 | 0.9134 (1371 of 1501) | **0.9454** (1419 of 1501) |
| R@10 | 0.9627 (1445 of 1501) | **0.9813** (1473 of 1501) |
| median rank | 1 of 300 | 1 of 300 |
| mean rank | 4.0 of 300 | 2.3 of 300 |
| chance R@1 | 0.0033 | 0.0033 |

Both columns are this one test, before and after the query transform below: the
test embeds through `embed_query`, and the left column is the run that predates
it. The right column is what the product does today.

Latency does not move with it — the transform is string work in front of the same
single encoder pass. The post-change run is its own control: it printed 312 ms per
image against 260 ms on the *indexing* half, a path the change does not touch at
all, on a machine that was downloading a model at the time. So the timings stand
as the clean run measured them: **77.9 s to index**, 260 ms per image, and **98.4
s for 1501 queries**, 66 ms per query. The 82 ms in the later run is the same load
that 312 is, and neither figure is the one to quote.

Ties are broken against the model: a caption's rank is one plus the number of
images scoring *strictly* higher, so an image level with the right answer counts
as beating it. Every caption is a query, so one lucky retrieval moves the
headline by 0.07 percentage points rather than 9.

### What this number means

The 0.85 that was asked for is **met at rank 5 and missed at rank 1** — on this
300-photograph baseline; the growing-library curve near the end of this file is
not flat, and both readings thin out as the shelf grows. Read as top-1 accuracy,
description search is at 70%; read as "the right photograph is in the first row
of results", it is at 95%. Both readings are honest and they answer different
product questions, so the target cannot be scored until it is said which one it
meant. Nothing in `docs/product-definition.md` sets a numeric bar for this
feature — it asks for a "CLIP text↔image embedding space for description queries"
and says nothing about recall — so this is the one number in this file the
repository cannot supply a reading for on its own.

This is the first measurement on which mechanism comparisons are meaningful. 300
images and 1501 queries resolve a difference of a few percentage points; the
eleven-photo set resolved 9.1 points per item and had already been queried often
enough that tuning against it would have been fitting noise.

Cost per image is a real constraint and is measured above: 260 ms to index one
photograph is fine for a library import and unacceptable for anything
interactive, and 66 ms per query is what a keystroke can afford only with
debouncing. Any fix that adds a second encoder pass per query multiplies that 66
ms, which is why the combined export was rejected on cost rather than on
quality.

### The query was worth more than the model — and it is shipped

Before spending anything on a better encoder, the query itself was fixed. It cost
nothing, and it moved rank 1 further than either mechanism below moves it.

Captions written by annotators are sentences. The tower was trained on alt text,
which is lower case and ends without a period, so a sentence is off-distribution
for it. Five transforms, same 1501 captions, same images, one harness:

| query transform | R@1 | R@5 | R@10 | mean rank |
| --- | --- | --- | --- | --- |
| as written — the shipped path until this change | 0.6629 | 0.9121 | 0.9660 | 4.04 |
| first letter lower-cased | 0.6849 | 0.9287 | 0.9734 | 3.56 |
| whole query lower-cased | 0.6962 | 0.9394 | 0.9827 | 2.34 |
| lower-cased, trailing period dropped — **shipped** | **0.7075** | **0.9420** | **0.9833** | 2.28 |
| lower-cased, period *and* commas dropped | 0.7089 | 0.9440 | 0.9840 | 2.27 |

The last row is the one the harness found first, and commas are deliberately not
in the shipped transform: they are worth +0.0014 R@1, two queries of 1501, and
deleting punctuation a person typed, for two queries in 1501, is not a trade
worth making. `SiglipEmbedder::normalise_query` lower-cases, drops the trailing
period and trims, and `embed_query` applies it before the text tower sees
anything.

In the engine, through that path, the test above moves from 0.6582 to **0.7015**
R@1 and from 0.9134 to **0.9454** R@5. The harness's 0.7075 and the engine's
0.7015 sit 0.6 points apart, which is the same resize-rounding offset that
separates the two raw columns from each other.

**The transform that needed proving is the one that touches capitalisation.**
Lower-casing is a no-op on a typed fragment, so on the query shape the product
mostly receives it can only be harmless; the risk runs the other way — that a
query *carrying* capitals loses information. It does not. Split on the 61
captions that have a capital after their first character — proper nouns, brand
names, `Goodmayes Boys' School`:

| subset | n | R@1 as written | R@1 normalised | mean rank |
| --- | --- | --- | --- | --- |
| a capital after the first character | 61 | 0.3770 | **0.7705** | 33.38 → 2.69 |
| no such capital | 1440 | 0.6750 | 0.7049 | 2.79 → 2.26 |

The subset capitalisation was *for* is the subset that gains most — 39 points at
rank 1, mean rank from 33 to 3. Those are the off-distribution queries: a
capitalised token is one the tower barely saw in that position, and normalising
pulls it in rather than erasing it.

What this does **not** buy is a faster or better typed fragment. `--describe "a
dog on grass"` is already lower case with no final period, so the transform is the
identity on it, and every point above is on sentence-shaped input. Saying so
matters more than the number does: a reader who takes 0.7075 as "the search box
got four points better" has been misled by a number measured on sentences.

**A prompt ensemble was measured and not shipped.** Averaging the text vector
with `a photo of ...` and `a picture of ...` took R@1 from 0.7075 to 0.7135 — nine
queries of 1501, half a standard error — for a second encoder pass per query,
which doubles the measured 66 ms. It also retires the four-point gain this file
previously attributed to ensembling: that measurement had the lower-casing
*inside* its templates, so what it measured was the case fix. An ensemble with no
case fix scores 0.6562, worse than the raw query alone at 0.6629.

### Three mechanisms this corpus ruled out

Two mechanisms were the obvious candidates for the remaining 30% of rank-1
misses. One was image geometry at ingest: the engine stretches every photograph
to a square and throws the aspect ratio away doing it. The other was matching
against several crops of an image instead of one whole-image vector, because an
object that fills a corner of the frame is a small fraction of a single pooled
vector. Both are measured here, and neither is worth building. The third is not
an ingest change at all — it is the standard inference-time response to a flat
embedding space — and it is measured last.

The harness that measured them is a Python script outside this repository, which
is a gap: unlike the COCO baseline above, nothing here can be re-run from the
repository today. It had to earn its place before its numbers were worth
recording, and it did: its first variant is the shipped preprocessing, and it
lands at **R@1 0.6629** against the Rust engine's 0.6582 — both with the caption
embedded as written, the left column above. Seven queries out of
1501 move between the two, which is the resize filter — Pillow's BICUBIC against
the engine's CatmullRom — and not a difference in method. Every comparison below
is between variants inside the one harness, so that offset cancels.

**Ingest geometry does not help.** The engine stretches every photograph to a
square, discarding aspect. Three alternatives, same 1501 captions, same images:

| preprocessing | R@1 | R@5 | R@10 | mean rank |
| --- | --- | --- | --- | --- |
| stretch to 224x224 — **shipped** | **0.6629** | 0.9121 | 0.9660 | 4.0 |
| shortest side to 224, centre crop | 0.6409 | 0.9147 | 0.9640 | 3.9 |
| longest side to 224, centre crop | 0.6209 | 0.9054 | 0.9567 | 4.1 |
| letterbox to 224 on grey 127 | 0.6302 | 0.8994 | 0.9494 | 4.2 |

The shipped stretch is the best of the four at rank 1, by 2.2 points over the
closest alternative and 4.2 over the worst. Distorting aspect, it turns out, is
not the problem.

That finding retires a reading these sections invite. This file sets 0.545 top-1
— eleven photographs, a harness — beside 0.455 top-1 — eleven photographs, the
engine — and notes that the two differ in that one way. The juxtaposition
suggests geometry accounts for the gap. It does not: on 300 photographs
centre-cropping is the *worse* method, so whatever moved those eleven items, it
was not the aspect ratio.

Nothing here contradicts itself; the problem is that eleven items cannot carry a
comparison, and this file asked them to several times. They are enough to reject
a configuration that is broken — unpadded text collapsing to 0.091 is one of
those, and that rejection stands. They are not enough to rank two configurations
that work. The corpus above is the instrument for that, and it is the one to use
from here.

**Multiple vectors per image buy rank 5 and cost ten times the indexing.** Nine
overlapping crops per photograph — 3x3 at half size, so each is a quarter of the
frame — plus the whole image; ten vectors per image, matched two ways:

| matching | R@1 | R@5 | R@10 | mean rank |
| --- | --- | --- | --- | --- |
| whole image only — **shipped** | **0.6629** | 0.9121 | 0.9660 | 4.0 |
| best of the 10 vectors | 0.6356 | 0.9147 | 0.9647 | 4.0 |
| mean of the best 3 | 0.6576 | **0.9307** | **0.9680** | 3.8 |

Taking the maximum over ten vectors is *worse* at rank 1 than taking the whole
image alone: a crop that happens to match is a false positive, and ten chances
to match is more of them. Averaging the best three recovers to 0.6576, within
0.0053 of the baseline, and gains 1.9 points at rank 5 — for ten encoder passes
per photograph instead of one.

The cost decides it. A crop measured 362 ms and a whole image 391 ms in the same
run under the same load, so a crop is not cheaper than an image and ten vectors
per photograph multiplies indexing by about ten: at the engine's measured 260 ms
per image, a 600-photo library goes from about 2.5 minutes to about 26. There is
no batched shortcut hiding in it either — the vision tower does accept a batch,
but 16 images in one call took 447 ms per image against 575 ms for a single
call, a factor of 1.3 where the arithmetic suggests 16. Batching also moved the
pooled vector: the same image run alone and run as row 0 of a batch of five gave
cosines of 0.9973, so it is not perfectly free even where it is fast.

Those last two timings were taken while another job held the machine, so treat
the absolute milliseconds as an upper bound; the ratios, which are what the
argument uses, come from rows measured back to back.

Neither mechanism is implemented. The two tables above are the argument for
rejecting them, not a description of anything the engine ships: 0.7015 R@1 and
0.9454 R@5 with the stretch at ingest, one vector per photograph and the query
transform above remain the engine's numbers.

**Whitening the space removes the alignment along with the flatness.** If a flat
space costs precision in the ambiguous middle, the standard inference-time fix is
whitening: centre the embeddings, rotate them onto their principal axes and
rescale each axis to unit variance. It needs no labels and no trained projection,
only the library's own vectors, which the engine has at index time — so unlike
the pooling alternatives it is a mechanism that could have shipped.

It was measured with a held-out split, because a transform fitted on the images
it is then scored against proves nothing: the transform is fitted on half of the
300 photographs, applied to both sides, and scored on the other half with the 750
captions those images own. Chance over 150 candidates is 0.0067. Dimension counts
are separate fits, not truncations of one. The harness is the same
outside-repository Python script the geometry and crop tables came from — the
same gap, stated once — and before it changes anything it reproduces the shipped
configuration's 0.7075 to four decimals, on the full 300 candidates.

| transform fitted on | R@1 | R@5 |
| --- | --- | --- |
| nothing — the shipped configuration | **0.7787** | 0.9800 |
| centring only, the image mean removed | 0.5840 | 0.9160 |
| whitening on the fit images, 768 / 384 / 256 dims | 0.0067 | 0.0373 |
| whitening on the fit captions, 768 dims | 0.0853 | 0.2267 |
| whitening on the fit captions, 384 / 256 dims | 0.5280 / 0.6493 | 0.7627 / 0.8813 |
| whitening on images and captions together, 768 / 384 / 256 dims | 0.1493 / 0.5773 / 0.6333 | 0.3107 / 0.7987 / 0.8853 |

Every variant is worse than doing nothing, and the sharpest result is the
simplest one: whitening fitted on images alone lands **exactly on chance**. That
is not an implementation failure, it is the answer. The large shared component is
what the two towers *agree* on; a transform fitted in the image space and applied
to text moves the text vectors somewhere the images no longer are, which is why
the two sides come out unrelated. Even fitted on captions, and applied to both,
whitening subtracts the direction that carries the cross-modal match. Five
regularisation values from 1e-5 to 1e-1 times the mean eigenvalue move R@1
between 0.0067 and 0.0227, so it is not a tuning problem; and fitting on all 300
images — the leaky, most favourable version, which is what the engine would
actually do — gives 0.0933, so the held-out split is not what makes it fail.

Two things follow. The flatness is not a *covariance* to be corrected at query
time — fp32 said the same thing about the weights, and this says it about the
space itself. It is not the last word on query-time transforms either: removing a
mean rather than a covariance gains points everywhere it was measured, at the end
of this section, and the row above is the *image* mean rather than that one. And
the baseline in this table is worth reading twice — 0.7787 with 150 candidates
against 0.7075 with 300, same model, same captions, half the library. Rank 1 gets
easier on a smaller shelf, so this feature's headline is a number about a library
size rather than a constant.

### A second encoder, measured — and it does not take the ranking

0.7015 says what SigLIP Si16-base does, not what the task allows, so a second
encoder was run on the same corpus: `siglip2-base-patch16-224`, the
`onnx-community` export at revision `ba1f3b08`, the same 300 photographs and the
same 1501 captions, each model preprocessed as its own config declares. SigLIP2
asks for bilinear resampling where SigLIP asks for bicubic; both ask for a stretch
to 224 with mean and standard deviation 0.5, and both got what they asked for.

**The export that runs is not the export it advertises.** The published
`vision_model_int8.onnx` cannot load at all: it contains a `ConvInteger` node, and
ONNX Runtime's CPU provider — Python and the Rust engine alike — has no kernel for
it, so an adoption would have had to begin by finding a different quantisation.
The same revision publishes a second and different quantised blob,
`vision_model_quantized.onnx` (byte-identical to `vision_model_uint8.onnx` by
digest, and *not* to `vision_model_int8.onnx`), and that is the one measured here.

| model, text form | R@1 | R@5 | mean rank | matched - mismatched |
| --- | --- | --- | --- | --- |
| SigLIP base, captions as written | 0.6629 | 0.9121 | 4.04 | +0.1369 |
| SigLIP2 base, captions as written | 0.5050 | 0.8081 | 6.69 | +0.0908 |
| SigLIP base, shipped query form | **0.7075** | **0.9420** | 2.28 | +0.1496 |
| SigLIP2 base, shipped query form | 0.5363 | 0.8348 | 4.34 | +0.1024 |

Like for like, SigLIP2 loses 15.8 points at rank 1 with the captions as written
and 17.1 in the shipped query form. Normalisation is worth +4.5 to SigLIP and +3.1
to SigLIP2, so it is not the explanation — it widens the gap slightly rather than
closing it. Every number in that table comes from one harness over the same corpus
with the same scoring, and the caption-to-image ordering was re-derived from the
manifest and compared index by index against the original before any of it was
believed.

**A weaker space, not a broken one.** The harness's own alignment check — "is a
caption closer to its own photograph than to another caption?" — condemns SigLIP
v1 as well, at +0.0824 against +0.7219, so it was measuring the wrong direction:
those same-modality numbers are the anisotropy this file has recorded three times
now. What separates a working pair from a broken one is the margin between matched
and mismatched *cross-modal* pairs, and SigLIP2's is positive and smaller, +0.10
against +0.15. The text tower is healthy on its own — ranking every caption
against the other 1501, SigLIP2 puts 2.051 of a photograph's 4 remaining captions
into its top 5 where v1 puts 2.129, the same structure within 4% — so the loss is
cross-modal, which is also what a damaged or mismatched *vision* export would look
like. That possibility is not excluded here: the fp32 pair (1.45 GB) was not run.

What is excluded is the reason to spend that download. The export that runs is
worse by 16 to 17 points and the one that does not run cannot ship. The runnable
pair is 378 MB of weights against the shipped pair's 211 MB, with a text tower 2.5
times the current one in the query path, where a query costs a measured 66 ms; and
the repository carrying the export declares **no licence** while its base model is
apache-2.0. A good number could justify that work — this is not one.

The harness for this comparison lives outside the repository, the same gap the
geometry, crop and whitening tables carry. It prints the sha256 of every file it
loads, so the three artifacts are identifiable: vision `5f2b401c...`, text
`3a0603d3...`, tokenizer `cb9140fa...`.

### The one transform that gains, and the constant it would need

This belongs next to the whitening result above, because it removes a **mean**, not
a covariance, and that difference is the whole finding. It is measured by a test in
this repository — `coco_retrieval.rs`,
`a_query_side_mean_can_be_scored_on_a_held_out_half` — which embeds the corpus
through `SiglipEmbedder` and fits each mean on one half of the photographs,
scoring the other half's captions with all 300 images as candidates:

| mean removed, fitted on half the corpus | R@1, fit on evens | in/out | R@1, fit on odds | in/out |
| --- | --- | --- | --- | --- |
| nothing — the shipped configuration | 0.6907 | — | 0.7124 | — |
| the images' mean, both sides | 0.5280 | 40/162 | 0.5579 | 22/138 |
| each side its own mean | 0.7000 | 52/45 | 0.7390 | 55/35 |
| the captions' mean, both sides | 0.7320 | 63/32 | 0.7603 | 59/23 |
| images' and captions' mean, both sides | 0.7413 | 71/33 | 0.7483 | 57/30 |
| **the captions' mean, query side only** | **0.7333** | 66/34 | **0.7537** | 61/30 |

Which mean gets removed decides the sign. The images' own mean applied to text
vectors costs fifteen points, for the reason whitening-on-images lands on chance:
it moves the text somewhere the images are not. The captions' mean is the direction
that helps, in both directions of the split, and it helps whether or not the
stored vectors are shifted with it — 0.7333 and 0.7537 with the images untouched
against 0.7320 and 0.7603 with them shifted. That is what a shippable version would
need: the transform on the query side only, so no re-index and no model change,
just the constant.

How much of the mean to remove is not a knife edge. Query side only, at 0.25, 0.5,
0.75 and 1.0 of it, R@1 is 0.7213 / 0.7227 / 0.7360 / 0.7333 in one direction and
0.7337 / 0.7430 / 0.7550 / 0.7537 in the other; 1.0 is the simplest value at the
top of that range.

**What stops it is that the constant has to come from somewhere.** The mean above
is fitted on COCO captions, and a user types something else. Rewriting the queries
into two other styles over the same labels — the only transfer test this corpus
allows — a caption-fitted mean helps in all six cells and hurts in none, but by an
unstable amount:

| query style | raw R@1 | centred R@1 | delta | in/out |
| --- | --- | --- | --- | --- |
| captions, the fitted style | 0.7067 / 0.7084 | 0.7480 / 0.7470 | +4.1 / +3.9 | 68/37, 59/30 |
| stopword-stripped keywords | 0.6533 / 0.6538 | 0.6760 / 0.6991 | +2.3 / +4.5 | 66/49, 70/36 |
| first four words | 0.2613 / 0.2517 | 0.2707 / 0.3103 | +0.9 / +5.9 | 59/52, 89/45 |

The two styles are the outside harness again, written out in
`centre_transfer.py` rather than described, and the stopword list is a standard
one: it was not tuned to this table. Read together with the row above, a
caption-fitted constant is a corpus artefact wearing a transform's clothes. It is
scored against the same 1501 captions that produced it, and the library it would
ship to has no labelled descriptions at all, so nothing here measures what it
would do there — and the effect it is *for* is 4 points at rank 1, a real gain but
not one that obviously justifies shipping a constant fitted on a corpus the user
has never typed against. It is therefore **not shipped**, and what would settle it
is a second labelled set (a hundred descriptions a person writes about their own
photographs would do) or fitting the constant on the user's own queries, which
needs a query history this product deliberately does not keep.
The deltas above are also measured on halves; what the constant does to the full
0.7015 is unmeasured, and taking that measurement is exactly the run a decision to
ship would begin with.

## Description search on a growing library — measured from 150 to 5,000 photographs

The whitening table already said the quiet part out loud: 0.7787 with 150
candidates against 0.7075 with 300, same model, same captions, half the library.
Rank 1 gets easier on a smaller shelf, so 0.7015 is a number about a library
size rather than a constant of the feature. This section measures the curve
instead of inferring it from two points: the full Karpathy caption split over
COCO 2014 `val` — **5,000 photographs and 25,010 human captions** — one
embedding pass, six library sizes scored from the same vectors.

**Provenance: measured, reproducible from this repository.**
`crates/core/tests/coco_retrieval.rs`,
`recall_is_measured_at_every_library_size_of_the_corpus`, `--release`, against
the corpus named by `TESSERA_CORPUS`
(`TESSERA_CORPUS_MANIFEST=manifest-5000.json`); the builder script and its
sources live beside the corpus, outside the repository (SECURITY.md), like every
other real-image corpus here. The 5,000 candidates are the whole split — all of
`val`, COCO ids ascending, short side never below 159 px — and each row selects
from them with the same evenly-spaced rule the corpus builder used (both ends
included, identity at 5,000). The **300 row is therefore the 300-photograph
corpus** of the sections above and prints that headline back exactly: 0.7015 /
0.9454 / 0.9813. The 5,000 row is 25,010 real caption queries rather than a
sample of them; the smallest row carries 751.

| library | queries | R@1 | R@5 | R@10 | chance | mean rank | R@1, change vs previous row |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 150 | 751 | 0.7909 | 0.9867 | 0.9947 | 0.0067 | 1.6 | — |
| 300 | 1,501 | **0.7015** | **0.9454** | **0.9813** | 0.0033 | 2.3 | −8.9 |
| 600 | 3,004 | 0.6155 | 0.8798 | 0.9554 | 0.0017 | 3.9 | −8.6 |
| 1,200 | 6,000 | 0.5288 | 0.7878 | 0.8813 | 0.0008 | 6.6 | −8.7 |
| 2,400 | 12,005 | 0.4444 | 0.7108 | 0.8067 | 0.0004 | 11.6 | −8.4 |
| 5,000 | 25,010 | 0.3552 | 0.6033 | 0.7040 | 0.0002 | 23.9 | −8.9 |

Reading:

- **Rank 1 decays linearly in the log of the library size — 8.4 to 8.9 points
  per doubling, no knee.** 33× the shelf costs 43.6 points of R@1: 0.7909 at
  150 photographs, 0.3552 at 5,000, with every step in between moving by 8.4 to
  8.9. Nothing in the six rows suggests the line flattening out.
- **The deeper ranks compound the loss.** R@5 stands at 0.6033 and R@10 at
  0.7040 when the shelf is 5,000, but their per-step cost grows with the shelf:
  R@5 sheds about 4 points on the first step and about 10 on the last, and R@10
  grows from about 1 to about 10. "The right photograph is in the first row"
  weakens faster than "it is the first result" does.
- **The ranking concentrates far better than chance at every size.** Mean rank
  grows 1.6 → 23.9 over 33× the library, where guessing would average 2,500, and
  chance R@1 at 5,000 is 0.0002 against a measured 0.3552. The model is not
  drowning; the shelf has outgrown the precision of the space.
- **The 0.85 bar is a statement about shelf size.** R@1 never reaches it at any
  size measured, best 0.7909 at 150 photographs. R@5 last clears it at 600
  (0.8798) and is at 0.6033 by 5,000; R@10 last clears it at 1,200 (0.8813) and
  is at 0.7040 by 5,000. On a library of thousands, no rank in this table
  reaches 0.85.

Honest caveats:

- One embedding pass, one run. Each row's queries are its own subset's captions,
  scored against that subset, so the table measures scale rather than sampling
  noise; a second pass would move the cells by run-to-run jitter, not re-order
  them. The pass ran while other work was on the machine — 297 ms per image and
  69 ms per query here, against the clean 260 and 66 in the latency sections
  above — which is why none of those timings is quoted as a latency result.
- The queries are captions, the same distribution as the labels. A person typing
  into a search box is not writing a caption — the same limitation the
  query-side mean runs into — and this corpus cannot lift it. The curve measures
  ranking under caption language.

## Where this leaves the feature

The headline number is now COCO: **0.7015 R@1 and 0.9454 R@5** over 300
photographs and 1501 real captions, measured through the shipped engine. The
eleven-photo set remains useful as an attribute-binding floor — **0.455 top-1
and 0.727 top-3** through the engine (`tests/image_retrieval.rs`), 0.545 top-1
in the harness above, which centre-crops where the engine stretches, against a
chance rate of 0.091 — but it is a stress test, not a baseline.

The eleven-photo corpus makes the task hard on purpose. Four of the eleven photos
are dogs and three of those are dogs on grass, so most of the ranking work is
attribute binding: "running through grass" against "sitting on grass" against
"with its tongue out". Three of the four miss at rank 1; two land in the top 3. A
cat face is retrieved as a dog. This is the documented weakness of single-vector
image-text models, and it is the part a better encoder alone is least likely to
fix.

The honest position: **description search works, is wired into the CLI, and can
be demonstrated today.** On COCO photographs it retrieves the right image at rank
1 for 70% of real captions and within the top 5 for 95% — for a 300-photograph
library; the curve section above carries the full-size result, and against 5,000
photographs the same shipped path gives **0.3552 R@1 / 0.6033 R@5 / 0.7040
R@10**. On screenshots the text arm already wins 0.964 and the image arm is not
the one doing the work. It is not yet a claim to put on a README: 0.70 at rank 1
is a good retrieval aid rather than the 0.85 the feature was asked for, and the
target recedes as a library grows — at 5,000 photographs even the top-5 reading
is 0.6033. The cheapest lever on it is measured and deliberately unshipped: a
query-side mean worth about +4 points at rank 1, held back because the constant
would be fitted on this corpus rather than on the language the user actually
types.

### What is not measured

The second encoder at fp32, and any label set that is not COCO. The same-corpus
encoder comparison that used to head this list has been run: **SigLIP2 base scores
15.8 to 17.1 points lower at rank 1** than the tower that ships, on the same 300
photographs and the same 1501 captions, so 0.7015 is not a number that survived
because nothing was compared against it. What is still unmeasured is that
comparison at fp32 (1.45 GB of weights), and a description corpus that is not
COCO — which is also the only thing that could decide the query-side constant
above.

A library larger than 5,000 photographs: the curve stops there because the
corpus does, and what the trend would do beyond the last measured row is an
extrapolation this document does not write down.

The caption arm as a retrieval route. It runs now — eleven of eleven photographs
produce a caption — but nothing indexes those captions and no retrieval number
has been taken from them. Four of the eleven captions shared a word with the
photograph's label, which is a floor for the arm being alive and nothing more.

Everything on macOS. The Vision OCR adapter is written and has never been
compiled or run on an Apple machine; the `macos-14` CI job is the gate, and until
it is green the adapter is unverified rather than working.

Image-side test-time augmentation. Averaging a photograph's embedding with that
of its mirror image, or over two scales, is the remaining cheap way to buy
robustness without a new model, and it costs a multiple of the 260 ms index time
for one stored vector. It has not been tried. It is listed rather than dismissed
because nothing else here bears on it: the nearest measured neighbour is the crop
family, which is a different transform and lost on this corpus.

## Document extraction in the Rust engine — measured (ticket 08)

The week-1 gate above blames the doc path on `pypdf`: 400 ms p50 to get text out
of one document, inside a ~1000 ms save→searchable. Both document pipelines are
now Rust — `pdf-extract` over `lopdf` for the text layer, a zip reader plus
`quick-xml` for DOCX — so the extraction term is measured again.

**Provenance: measured, reproducible from this repository.**
`crates/core/tests/documents.rs`, `document_extraction_latency_is_measured`,
`--release`, against the folder named by `TESSERA_DOCS_CORPUS`; one
`Pipeline::process` call per file — file load through page text and chunking,
which is the whole of extraction. Not the store, and not embedding. The run was
the only work on the machine.

Corpus: **70 RFC PDFs** (RFC 2616 and the 8650–9457 range — the modern series
whose PDF renditions rfc-editor.org publishes — 27.9 MB) and **44 DOCX** (7.0
MB): the 40 largest by size in Apache POI's public `test-data/document` fixtures
plus the four `.docx` files in python-docx's `tests/test_files`. Real documents
out of two production toolchains, public downloads, kept outside the repository
like every other corpus (SECURITY.md).

| format | files | MB | p50 | p95 | mean | no text | failed |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| PDF | 70 | 27.9 | **77.1 ms** | 471.8 ms | 140.2 ms | 0 | 1 |
| DOCX | 44 | 7.0 | **2.4 ms** | 9.6 ms | 4.4 ms | 7 | 6 |

Reading:

- **The pypdf-bound term is gone.** 77.1 ms p50 against the spike's 400 ms. The
  corpora and the runtimes differ — the spike extracted 40 mixed personal
  documents in Python, this extracts RFC-sized PDFs in Rust — so the honest
  reading is that this term moved from hundreds of milliseconds to tens, not
  that some exact factor belongs to a library swap.
- **DOCX extraction is negligible**: 2.4 ms p50 means the cost of a Word file
  is its embedding, not its reading.
- **The tail is the large documents.** p95 471.8 ms belongs to the megabyte
  class of the corpus (the biggest file is RFC 9110, 2.9 MB); the median file is
  tens of KB and tens of ms. The spread in file size is the spread in time.
- **What this does not measure is save→searchable**, so the week-1 gate line is
  not rewritten by it: the extraction term it blamed is now 77 ms, but
  chunking, embedding and the store were not re-measured in this configuration.
- **One PDF made the parser panic, and the guard is what turned it into a
  recorded failure.** RFC 8671 trips `pdf-extract` into a `panic!`
  (`wrong type`) rather than returning an error; `catch_unwind` in the pipeline
  records that one file as failed with the reason — *"the PDF parser panicked
  (wrong type); the file is recorded as failed and the run continues"* — and
  the other 69 PDFs complete. Without the guard, one damaged PDF would end the
  index run. The default panic hook still prints its two lines to stderr; the
  record in `tessera stats` is the reason.
- **Six DOCX failed, all on a zip that will not open**: two password-protected
  documents (a real-world category — an encrypted OOXML file is an OLE compound
  file, not a zip) and four truncated clusterfuzz fixtures from POI's corpus.
  Each is recorded failed with its reason and the run continues; all seven
  failures are retried on the next `tessera index`, because a failed file is
  pending work rather than a tombstone.
- **Seven DOCX carry no body text**, and that is a scope line, not a bug: the
  pipeline reads `word/document.xml`, so a document whose body is only an
  inline image (`having-images.docx`) or whose words live in headers and
  footers (`poi-headerFooter.docx`) indexes by name. Headers, footers,
  footnotes and text inside embedded images are not read in v0.1.

A scan is the other document shape, and its extraction is 0 ms of text on
purpose: a PDF whose pages carry no text becomes `status='awaiting_ocr'`,
counted as its own row in `tessera stats`, not searchable, and retried next run
— which is what makes the v0.1.x OCR pass an addition rather than a migration
(test `a_scanned_pdf_is_recorded_as_awaiting_ocr_and_visible_in_stats`).

The same corpus indexed end-to-end through `tessera index` in release: **107
indexed, 7 failed, 0 awaiting** — the failures and the panic record are the same
files as the table, and `tessera stats` lists each by name with its reason.

**Caveats.** Single machine, single run, one file at a time; p95 over 70 and 44
files is a coarse quantile. The corpus is two open corpora rather than a
personal Documents folder, so "RFC-sized" describes these files rather than
anyone's. The DOCX side is the 40 *largest* POI fixtures, so sub-20 KB Word
files are a minority there (the four python-docx fixtures are that minority).
And extraction is not the whole document story until save→searchable is
re-measured end to end.

## The text arm in the Rust engine — measured (ticket 09)

The spike measured a text arm in Python (35.0 ms p50 for one MiniLM query), but
until now the engine had none: neither document chunks nor OCR text carried a
vector, and meaning was not a way to search. It is now a real arm —
`crates/core/src/vectors/minilm.rs`, one 384-d vector per tile in `txt_vec`,
filled by a post-walk sweep — and `tessera search --describe-text` is its query
surface until ticket 10 fuses the arms into one box.

**Provenance: measured, reproducible from this repository.** The query-side
number is `crates/core/tests/text_arm.rs`,
`query_embedding_latency_is_measured` (ignored; run with the pinned `minilm`
set installed), `--release`, 40 samples after one warm-up pass, the run the
only work on the machine. The end-to-end numbers are `tessera index` and
`tessera search --describe-text` over the corpus of the ticket-08 section
above: 70 RFC PDFs and 44 DOCX, 107 files indexed, 7 recorded failures, one
file at a time.

| Measure | Result | Runs |
| --- | ---: | ---: |
| Query embedding (MiniLM int8), p50 | **20.6 ms** | 40 |
| Query embedding, p95 | 23.2 ms | 40 |
| Full meaning query, 6,425 chunk vectors in `txt_vec` | **43–45 ms** | 6 |
| First `tessera index` pass: walk + extract + embed 6,425 chunks | 154.8 s | 1 |
| Re-index of the untouched corpus: 0 chunks embedded | 7.8 s | 1 |

Machine: the one in **Hardware** above (AMD Ryzen 3 5300U, 8 threads); the
MiniLM session runs on 8 threads, as the CLI clamps it.

Reading:

- **The spike's "tens of milliseconds" held.** 20.6 ms p50 here against the
  spike's 35.0 ms, measured in a Python script in week 1. Different runtime,
  different sample set, so read it as "the same class, confirmed in the engine
  that ships it" rather than as a speedup claim about a library.
- **A full query is roughly embed plus scan.** 43–45 ms total: ~21 ms of query
  embedding, the rest the brute-force cosine scan over all 6,425 vectors and
  the store reads. There is no ANN index and none is needed at this size — the
  same choice the image arm's section records; the scan is the term that grows
  linearly with the corpus.
- **Indexing pays the same per-chunk cost.** 154.8 s for the first pass with
  extraction included (ticket 08 measured extraction in the tens of ms per
  file); setting that aside puts the sweep at about 21–22 ms per chunk, the
  query-pass cost again, because it is the same ONNX call.
- **The steady state is free.** The second pass over the untouched corpus took
  7.8 s and embedded 0 chunks: the sweep asks the store which tiles have no
  vector and the answer is none. A missing vector, a moved model pin and a
  fresh install are one repair path
  (`Store::tiles_without_text_vectors`), which is also what will make ticket
  11's watcher affordable — new text is embedded once, and nothing else moves.
- **The known-answer check is a test, not an anecdote.** `text_arm.rs` builds
  three small files, asks for "the contract that stops me working for a
  competitor", and requires the lease first — while asserting that the lease's
  text does not contain the word *competitor*, so the match cannot be explained
  by the words.

A pin that moves is not a silent blend: `tessera index` drops the whole text
arm when the manifest's MiniLM pin differs from the version recorded in `meta`,
and the sweep rebuilds it from the tiles already stored — the text is never
re-read for this. The image arm's pin has no equivalent drop-in path yet (its
only writer is the image pipeline, per file), which is left as it is rather
than half-fixed here.

**Caveats.** One machine; one indexing pass; six query runs whose range is the
whole spread, not an interval; p95 from 40 embeddings of short sentences, so
the 256-token cap is not exercised. The corpus is two open corpora rather than
a personal Documents folder, and 6,425 chunks is a small index — the scan half
of the query has not been measured beyond it, and no retrieval-quality metric
for meaning search over documents is claimed here.

## Hybrid fusion — measured (ticket 10)

Three arms now answer one query by default: the lexical list (FTS5/BM25), the
image list (SigLIP) and the text list (MiniLM) merge by rank position, each
arm's vote scaled by how much text the file carries (ADR-0003's amendment:
Full 1.0 / 0.05 / 1.0, Little 0.5 / 0.5 / 0.5, None 0.0 / 1.0 / 0.0).
`tessera search` runs the fused path; `--describe` and `--describe-text` stay
as arm-isolating diagnostics rather than modes.

**Provenance: measured, reproducible from this repository.**
`crates/core/tests/fusion_search.rs`, `fused_search_latency_is_measured`
(ignored; run with the pinned `siglip` and `minilm` sets installed),
`--release`, against the docs index the ticket-09 section describes (6,425
chunk vectors, no image vectors): 40 searches — eight distinct queries rotated
five times — after one warm-up pass per query, 4 intra-op threads per model
(the measurement convention; the CLI uses min(cores, 8)), the run the only
work on the machine.

| Stage | p50 | p95 |
| --- | ---: | ---: |
| **Fused search, all three arms** | **141.3 ms** | **157.0 ms** |
| lexical arm | 48.2 ms | 117.0 ms |
| image arm (SigLIP query encode, nothing to rank) | 72.8 ms | 82.3 ms |
| text arm (MiniLM query encode + full collapse) | 101.5 ms | 119.6 ms |

A re-run discipline worth stating: two more idle-machine runs of the same 40
samples read total p50 136.2 ms and 133.2 ms, each arm's p50 moving by at most
about 6 ms; one run taken right after a release build read 155.3 ms p50 /
236.0 ms p95. The table is one run of the four; read the totals as a band of
roughly ±10 ms on this machine, not a constant.

Reading:

- **The product target is not met, and nothing here pretends it is.**
  `docs/product-definition.md` asks for query end-to-end < 100 ms at 50k
  items. This index is 6,425 chunks, not 50k, and the fused query is already
  141 ms p50. Two costs dominate and both are model work, not I/O accidents:
  SigLIP's query encoding (~73 ms, paid whether or not there are image vectors
  to rank) and the text arm's full scan + tile→file collapse (~102 ms, ~21 ms
  of it the MiniLM query embed the ticket-09 section measures). The arms run
  on threads, so the wall is roughly the slowest arm plus ~40 ms of shared
  work: a store connection per thread, the evidence pass over the union of the
  arm lists, the fusion itself, and rendering the final hits. `tessera search`
  prints the same decomposition on stderr (`searched in 141 ms (keyword 48 ms,
  image 73 ms, meaning 102 ms)`).
- **Arm rows are wall times measured while the other arms run.** The machine
  has 8 hardware threads and each ONNX session is built with 4, so the two
  encoders contend. The text arm measured alone is the ticket-09 row — a full
  meaning query at 43–45 ms; ~102 ms is what it costs sharing the machine
  with the image arm. Read the per-arm rows as a breakdown of one fused query,
  not as standalone costs.
- **Fusing cost two fixes to the collapse, both measured here.** The first
  measured cut of the same test read 167.2 ms p50 (p95 212.3): the tile→file
  collapse fetched every ranked chunk's text — a JOIN plus the text column per
  chunk — in 200-id batches. Identity-only rows (`SELECT id, file_id`) and
  1000-id batches brought the total to 141.3 / 136.2 ms and the text arm from
  126.9 ms to ~100 ms. The sweep that chose the shipped constant now
  re-derives its numbers through the production `fuse` rather than a copy of
  it (`tests/image_fusion.rs`) and reproduces the image-arm section's curve:
  top-1 0.964 held through weight 0.05, 0.857 at 0.10, 0.375 at equal weight.
- **One box, on a mixed folder — the exit demo.** The demo test
  (`a_real_folder_answers_one_query_with_every_arm`, ignored) indexed a 13-file
  folder: three RFC PDFs, one DOCX (an airline refund line), two text files,
  six real screenshots and one rendered-text invoice PNG (a synthetic control,
  labelled as one). `invoice airline` came back docx first
  `[keyword, meaning]`, then the invoice PNG `[keyword, image, meaning]` — one
  hit wearing all three arms — then text, screenshot and an RFC page by
  meaning: the ticket's "screenshot AND PDF page AND docx from one query".
  The phrasing the ticket wrote down, `the invoice from the airline`, returns
  the same files through the semantic arms alone — no single file contains all
  four words, and the lexical arm ANDs its terms — recorded here because a
  reader will type that sentence. `type:image` returned a filter-only listing
  of exactly the seven images, with no arm labels because no arm ran; the
  re-run over the untouched corpus indexed nothing and took 0.2 s.

**Caveats.** One machine; 40 samples over eight queries, so the quantiles are
over repeats of a small query set, not a query distribution; the index holds
no image vectors, so the image arm's *ranking* half contributes nothing here
(its encoder does); the demo is 13 files, which shows the merge but says
nothing about retrieval quality at scale; the Little and None rows of the
weight table are unmeasured defaults; and 50k-item scale is untouched — both
scan terms grow linearly with the corpus (the two sections above say what
that costs).

## Watch mode — measured (ticket 11)

**Method.** `target/release/tessera.exe`, the installed pinned model sets, and a
synthesised corpus of 400 small `.txt` files (one tile each, so 400 MiniLM chunks
when the sweep runs). Everything is measured from outside the process: the
watcher's own stdout for the phase boundaries, and Windows process counters for
RAM and CPU. The script is committed at `scripts/measure-watch.ps1`, so the
numbers can be reproduced; it writes only to a temp directory. It was re-run on
2026-10-26 after the drain-detection bug in that script was fixed (a run under
concurrent machine load, not a quiet one): 7.58 s drain at 400 files
(53 files/s), save→row 0.98 s, save→searchable 2.73 s, idle 43.2 MB working set
/ 26.5 MB private. Same shape, with the drain figure moving with host load —
which is why the quiet-machine number below stays the headline.

| What | Measured |
|---|---|
| 400-file backlog, 4 workers, 400 chunks embedded | 5.52 s (73 files/s) |
| Save → row recorded, idle watcher | 0.93 s |
| Save → a query returning the file | 2.58 s (1.65 s of it the query process loading the model sets) |
| Idle after the drain: working set / private | 43.3 MB / 23.3 MB |
| Idle CPU over 5 s, queue empty | under 0.02 s (one sample; clock noise) |
| CPU over 5 s with 401 files queued, `--schedule paused` | under 0.02 s |
| The same paused run: working set | 14.8 MB |

**What the numbers say.** The drain is no longer paced by the loop: 73 files a
second, and the largest single part of that is the serial text sweep (400
embeddings), so the queue itself is faster than the headline. The loop parks on
the nearest timer it keeps — the 60 s rescan, the 30 s power poll, a retry
deadline — capped at one second, so an idle watcher wakes about once a second
instead of ten times. A delivered event wakes the loop immediately regardless,
so a file saved onto an empty queue is read as soon as notify delivers it: the
0.93 s is the drain's model load, not a poll interval.

The 0.93 s from save to row is mostly the drain's own model load. The watcher
drops the sessions when the queue empties — that is what makes the idle figure
43.3 MB rather than ~250 MB larger — so the first save after an idle period pays
their construction again. That is the trade the product definition asks for, and
it is the number to watch if the ceiling ever tightens.

The paused row is the one that says the queue is *held*, not busy: 401 files owed
and under 20 ms of CPU in five seconds. A pause that spun would have shown ~5 s.

**Caveats.** One machine and one corpus of 400 one-line text files: screenshots
or PDFs pay OCR and page extraction on top, which this mix does not, and the
drain figure would move with the mix. The save→row latency is one observation per
run, not a distribution over hundreds of saves. The 2.58 s includes a second
process starting cold, which is what a person typing a query pays, but the row
was searchable at 0.93 s. The two CPU figures are each a single five-second
sample, and repeat runs differ between 0.000 s and 0.016 s — at this scale that
difference is clock resolution, not behaviour; both mean "well under a
millisecond of CPU per second", which is what "not spinning" looks like from
outside. The drain figure likewise varies a few percent run to run (a concurrent
build put one run at 7.4 s), so 5.5 s is the figure for a quiet machine.

### A store outage is waited out, not spun through

`tessera watch` survives a store that refuses writes — a concurrent `tessera
index`, a backup tool, a WAL checkpoint — by reporting the failure, owing a
rescan and retrying on a backoff that doubles from 1 s to 60 s. The first version
of that wait cost a core, and the number belongs here because the log looked
idle while it happened: one line a minute, and 44% of a processor underneath it.

**Provenance: measured, reproducible from outside the process.** A second SQLite
connection renames the `files` table away from one live watcher (`--schedule
always`, a three-file corpus in `%TEMP%`) and leaves it renamed;
`Process.TotalProcessorTime` is sampled every 10 s. The probe is the QA round-3
script, kept in local working state at
`.scratch/tessera-v0.1/reviews/evidence/qa3-d2-resilience.ps1`; it writes only to
a temp directory.

| Into the sustained outage | CPU before the fix | CPU after |
|---|---|---|
| 10 s | 7.6 s | 9.0 s (of which ~4.1 s is the phase-1 recovery, not the wait) |
| 371 s | 170.8 s | 9.2 s |
| 668 s, a run that was not stopped | 296.6 s — 44% of one core | — |

Between the 10 s and 370 s samples the fixed run spends **0.17 s of CPU in six
minutes** — about 0.05% of a core, which is the rescan the backoff owes, not the
wait. Over the whole 841 s outage it spent 0.33 s, and it then ended by itself at
the twentieth consecutive failure (851 s in), naming the error, exactly as the
cap says it should. The retry lines are identical before and after (1, 2, 4, 8,
16, 32, then 60 s each, one per retry): the backoff was never the cost.

The mechanism was the wait, and only once a timer came due inside it. The
coordinator's loop sleeps until the nearest of its own timers — the 60 s rescan,
the 30 s power poll, a retry deadline — and reports an already-due timer as zero,
which for a working pass means "do not sleep, this pass has work to do". The
outage wait reused that answer, but the pass that waits runs no timer at all, so
from the moment the 30 s poll came due inside a backoff the "wait" was zero: a
tight loop, at millions of passes a second, until the retry deadline. Phase 1 of
the probe (a three-second outage) never lasted long enough to show it; only a
backoff longer than 30 s did. It is fixed by waiting for the rest of the backoff,
capped by the one-second shutdown tick, and a test now asserts that the loop
never asks the event feed for a zero wait while a retry deadline is still ahead.

## The 5,000-file milestone gate — measured (ticket 12)

**What was run.** The week 2–3 exit criterion (product-definition §5): a 5,001-file
mixed corpus indexed end to end by `tessera watch`, then the known-answer and
latency queries against that index. Everything below comes from
`target/release/tessera.exe` and Windows process counters; nothing is projected.

**The corpus.** 5,001 files: 2,000 text (1,203 real), 701 PDF (6 real), 500 Word
(2 real), 1,800 images (326 real). **Only 1,537 of 5,001 (31%) are real user
files**; the rest are generated documents and screenshots. There is no 5,000-file
real corpus on this machine, so this is the substitute, and the numbers should be
read with that in mind: generated text is cleaner, shorter and more uniform than
the real thing, and 1,474 of the images are rendered screenshots, which is the
easy case for OCR. The real-image sets span wallpapers, UI screenshots, design
references and test fixtures, 7 to 115 files each.

**Method.** Fresh index directory; `tessera watch --schedule always`; the drain is
the watcher's own banner line to its first `caught up` line (a 2 s poll bounds it,
so it is if anything slightly generous). Throughput divides corpus files by drain
seconds, so a file retried after a failure cannot inflate it. Peak memory samples
`WorkingSet64` and `PrivateMemorySize64` every 2 s for the whole drain, which on a
run this long is the peak, not a spot check. Latency is 5 queries × 8 repetitions
after one warm-up, parsed from the engine's own `searched in N ms` line — measured
after the embedders are built, so it is the search and not the model load a fresh
process pays. The per-arm figures come from the same line;
`scripts/measure-latency.ps1` reruns just that sweep against a finished index.
Hardware: Intel Core Ultra 5 225H (14 cores), 15 GB RAM, Windows 11 build 26200,
mains power, no build running.

|---|---|
| Files | 5,001 |
| Drain (`watch`, 4 workers, idle priority) | 685.8 s wall → **7.3 files/s** |
| Indexed / moved / skipped / failed / awaiting OCR | 4,999 / 0 / 0 / **2 files** / 0 |
| Chunks embedded | 17,154 |
| Index size | 113.7 MB → **22.7 MB per 1,000 files** |

**The two failures are corrupt files, not engine defects.** `real-pdf-0006.pdf` is

header`, which is the right answer. Each was retried once inside the run, which is

against a corpus of 5,001.

**Against the targets** (product-definition §6):

| Target | Result |

| Query end-to-end @ 50k items < 100 ms | **MISSED at 5,000**: 397 ms fused p50, of which the meaning arm is 310 ms |

| Document saved → searchable < 300 ms | **MISSED**: 0.98 s to the row, about 3× over |

**What the gate found that the tests had not.** Two Windows defects, both fixed
and covered: OCR could not be called twice concurrently — the engine's workers
collided inside `RecognizeAsync` — so the calls are now serialised; and a real
1440×21,142 capture was refused outright for exceeding
`OcrEngine::MaxImageDimension`, so such captures are now read in seam-safe bands
(`f5fb429`). The second is why the tall screenshot in the known-answer set returns
text instead of failing.

**Caveats, stated so they are not discovered later.**

- One machine, one run per configuration. Throughput varied 7.3 to 8.4 files/s
  across runs of the same corpus; the slower number is quoted. Only one image in
  the corpus takes the banded OCR path, so that fix costs seconds and does not
  explain the spread. The two latency passes agree within 2 ms (the gate run's
  own sample set gave 398 ms p50 / 504 ms p95).
- p50/p95 are over 5 queries × 8 repeats: p95 is effectively the near-maximum of
  32 samples, not an estimate of a query distribution.
- 50,000 items is unmeasured. Both scan terms grow linearly with the corpus, so
  50k will be worse than the numbers above, not better.
- Save→searchable at 5k was measured by the harness but not persisted by it; the
  row quoted is the 400-file `scripts/measure-watch.ps1` run below. The gate
  harness now records both save figures in its JSON, so the next run will carry
  them.
- The 31%-real corpus is the largest honesty gap here: a genuinely personal
  5,000-file folder is mostly PDFs, office documents and photos, and photos are
  the hard OCR case, not rendered screenshots.
